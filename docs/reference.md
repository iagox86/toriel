# toriel reference

**Status: working and verified (2026-10-20).** Daemon-owned sessions survive
controller restarts; the switcher opens at startup and lists ALL sessions
(live + inactive, grouped); lazy activation spawns a child on first prompt;
deactivate/kill/rename/group/delete all work; permission dialogs route
end-to-end with badge-and-block; two controllers share the list with
exclusive input attach and explicit take-over.

## Run

```fish
cd ~/projects/toriel
npm install                # once; symlinks the global pi + pi-tui
toriel              # auto-starts the daemon in the background if none is running
toriel kill-server  # stop the daemon (orderly: children shut down too)
toriel update       # what is behind: pi, the bundled packages, your own pi packages (`toriel update all|<name>` bumps)
toriel --isolated   # a separate instance for trying out a checkout (see "Developing toriel")
```

The daemon detaches and keeps running when the controller exits; restarting
a controller reattaches to everything. Multiple controllers can run against
one daemon. There is only ever one daemon per state directory: it takes a lock
(`daemon.pid` under `~/.local/share/toriel`, holding its pid) and a second one
refuses to start, naming the running pid, whatever socket it was given. A lock
left by a dead daemon is replaced. `kill-server` uses that pidfile and refuses to
signal anything that is not the toriel daemon. It names the code the daemon was
running, and after stopping it watches for about a second: a controller that is
still open somewhere starts a new daemon from ITS checkout at once, and
kill-server then says a new daemon (pid, build, folder) is already running.

## Which code is running

A daemon and a controller can come from different checkouts (a branch under test next to the real
install, or a daemon left over from before an update). The daemon's first message to every new
controller is `hello` (`src/shared.ts`): `protocol` (an integer bumped by hand when the message set
or a message shape changes incompatibly), `build` (`fingerprint`, `label`, `dir`, built by `build-id.ts`), `pid`, `sock`
and, for an isolated instance, `profile`. `DaemonLink` compares it with its own build on every
connect, including reconnects, in `compareDaemon` (`version-check.ts`):

- **Same protocol, same fingerprint:** nothing is said.
- **Same protocol, different fingerprint:** a warning (flash plus a standing `[daemon runs other
  code, see /doctor]` tag before the status line).
- **No hello at all:** the daemon predates this check, so it is older than the controller; also a
  warning, because whether it still works is not known.
- **Different protocol:** blocked. The link sends nothing but `list` and `shutdown` (a request
  rejects at once with the reason, a `send` flashes `not sent: ...`) and the tag says so.

The fingerprint hashes the content (not mtimes) of every `.ts` under `src/` and `pi/extensions/`,
computed once when the process starts, so the same code in two folders agrees and an uncommitted
edit shows. The label is for people: the git short hash with `+dirty` when `src` or
`pi/extensions` has changes, else the fingerprint (no `.git`, or no git binary). Nothing restarts a
daemon for you; the notice names `toriel kill-server` and says running sessions stop with it.
`/doctor` and `toriel doctor` end with a "Daemon" block (what runs where, then the verdict;
informational, it does not change the exit code). Bump `PROTOCOL` when a change makes an old daemon
or controller misbehave rather than merely lack a feature.

Not covered: a pi child keeps the extensions it was started with, but a daemon restart stops its
children, so a child cannot outlive the build that spawned it; if sessions ever survive a daemon
swap, record the build per session then.

## Developing toriel

`toriel --isolated [name]` (or `TORIEL_PROFILE=name`) runs a separate instance for trying out a
branch without touching the real one: its own daemon, socket, pidfile, data (groups, schedules,
grants, lineage, history), trash and daemon log, all under `$XDG_RUNTIME_DIR/toriel-<name>/`
(mode 0700, so cleared at logout). The name defaults to the folder the code runs from, so a
worktree names itself. The switcher shows `[isolated: name]`, `/doctor` prints the daemon's socket
and folder, and `toriel --isolated name kill-server` / `doctor` address the same instance. The
explicit variables (`TORIEL_SOCK`, `TORIEL_LOG`, ...) still win over the profile. Not isolated:
pi's own session files and settings under `~/.pi` (use a scratch working directory), and the
`--seed` idea from the ticket (copying groups in) is not built.

## Sessions opened in plain pi

Sessions created outside toriel show up in the switcher like any other
(toriel lists session files, regardless of who wrote them). To make their
liveness visible, load the **toriel-presence** extension into pi (it ships
in your extensions dir): every pi process then heartbeats the daemon, and
the switcher marks those sessions with a `[pi]` prefix and a dimmed name -
even before pi has written the session file (pi creates it lazily), the
live registration itself shows up as a switcher row; the session view shows
a LIVE-IN-PI tag. If that session is deleted elsewhere (e.g. pi's resume
picker) the row is dropped at the next prune tick instead of ghosting until
the heartbeat expires. toriel's OWN children are excluded (they are spawned
with `TORIEL_CHILD=1`, and the daemon also ignores registrations from their
pids), and presence heartbeats do not count as controller connections.

Prompting a pi-owned session asks first: "continuing here FORKS the
conversation (pi keeps its copy)" - enter again to fork it into a new
toriel-owned session (pi-native `--fork`) and deliver the prompt there, esc
to cancel. `/adopt` does the same fork without a prompt. If the session is
open in BOTH toriel (live child) and an external pi, prompting is refused
("close one before prompting here") - forking cannot help two live
writers. Adopting a session pi has not written to disk yet fails cleanly
("session file not found"); send one prompt in that pi first.

Unnamed sessions (brand-new, or forks still loading) display as
`<unnamed>`; the project directory stays visible in the description
column. For pi processes
without the extension, a file modified within the last 60s triggers a
warn-and-confirm (enter twice) before forking.

Node 22.18.0 or newer (`.nvmrc` pins the floor; the nvm default alias v20
will NOT run this - no type stripping). Children are normal pi processes
using your settings/auth/extensions.
The auto-started daemon uses the controller's own node binary, so it works
regardless of PATH.

## Keys

In a session: `ctrl-r` reverse-searches this session's history (type to filter, `ctrl-r` older, `ctrl-s` newer, `enter` use, `esc` cancel); `/` completes toriel's and pi's commands (fetched from the running pi via the daemon), `@`/paths complete files.

- `ctrl-s` - while messages you typed during a run are queued: send them now (ticket 222). A queued message is otherwise delivered at the next step (after the current model response and its tool calls); this stops the running step the way esc does (the partial answer stays, a running command is killed) and sends the queued messages together as the next prompt. Nothing queued, or already delivered: nothing happens; if the run cannot be stopped the texts go back in the box. Inside ctrl-r history search the key still means "newer"
- `ctrl-b` - while the agent works: move the subagent it is waiting for to the background, else the bash command it is waiting for (also `/background`; see "Background commands" and "Subagents")
- `shift+tab` - the mode key for the viewed session: normal -> auto mode (`/auto`; see "Auto mode" under "Permission grants") -> plan mode (`/plan`) -> normal (ticket 233; `src/mode-cycle.ts`, `SessionCommands.cycleMode`). Each step sends the same `auto_mode` / `plan_mode` commands the slash commands do, and the two are made exclusive: going to plan switches auto off, and a session with both on (set by the commands) goes to normal. A session with no id yet (nothing sent) skips plan, since the plan marker is named by the id. A completion popup keeps the key while it is open. The flag changes go out `quiet` (applied at once, no notice) and the one line saying which mode you settled on comes from the `mode_notice` command, sent when the presses have stopped for 5 s (`ModeNoticeDebounce` in `mode-cycle.ts`; protocol 15; ticket 236), so one burst is one line at any realistic press speed; and a burst that wraps around to the mode it started in says nothing at all, since nothing net happened. `/auto` and `/plan` still say so at once.
- `esc` - abort the running agent; messages still queued come back into the
  editor first (above your draft) so the abort does not deliver them
- `esc esc` on an idle session with an empty editor - rewind: pick an earlier
  message, the session is cut back to before it and the text returns to the

The transcript recognises the tags (live and on replay) and draws the usual command block; the switcher summary shows `$ cmd`. The first-message display fallback renders a bang-first session as `$ cmd` too, not as the wrapper text. It runs with the session's environment (`bangEnv` in `child-env.ts`): `TORIEL_CHILD`, `TORIEL_SOCK`, `TORIEL_SESSION_ID`, `PI_SESSION_ID`, `PI_SESSION_FILE` (all from the id the daemon learns once the session is up, forks included, because the environment is built when you press enter, not at spawn), and pi's bin directory first on `PATH`, as the agent's own bash has; `PI_PROVIDER`, `PI_MODEL` and `PI_REASONING_LEVEL` are left out (the daemon does not hold pi's ids). `TORIEL_CHILD` only gates which pi extensions load, so it does nothing for a plain command. `esc` stops it (`abort_bash`); ctrl-b cannot move it to the background; one command at a time per session; refused while compacting. `!!` is not offered. ## Semantics worth knowing

- Sessions have three states: active/processing, active/idle, inactive
  (file only). A deactivated session's transcript still renders from the
  file; typing a prompt respawns the child with `--session <file>`.
- Input on a live session is exclusive: entering attaches you; another
  controller entering is refused, and a second enter takes over (the old
  driver becomes VIEW-ONLY). Viewing/scrollback is never exclusive - every
  controller receives every event stream.
- Deletes never unlink: the session file moves to
  `$XDG_DATA_HOME/toriel/trash/` with a `.json` manifest (original path +
  timestamp), because the session file is the only copy that exists.
  Groups live in `$XDG_DATA_HOME/toriel/session-groups.json`.
- Permission dialogs: toriel has no permission system of its own. Children that load
  the `pi-permission-system` package (bundled with toriel, or the user's own copy listed under `packages` in pi's `settings.json`;
  its rules are `~/.pi/agent/extensions/pi-permission-system/config.json`) block on
  ask-listed tools, and any extension's confirm/select/input dialog is handled the
  same way; the dialog routes to the attached controller (y/n, digits for
  select, esc cancels select). The dialog is labeled with the session that
  raised it (e.g. "Session 3 'Worker'", id alone when unnamed) in its title
  and the status-line hint. Unattached or unanswered dialogs keep the
  child blocked, and a fresh controller sees the pending dialog (badge `!`,
  re-sent on attach). No timeout anywhere.
- Transcript replay renders tool calls/results from the session file,
  matching the live view (args matched from toolCall blocks).
- Known gap: a ctrl-chord in the first second after start can be swallowed by
  pi-tui's keyboard negotiation.

## Settings

`~/.config/toriel/settings.yaml` (`$XDG_CONFIG_HOME`, or `TORIEL_SETTINGS` for
a different path; a YAML file, so it can carry comments, and a JSON file reads too). The daemon creates it on first start (and `toriel doctor --fix` does when it is missing) with every setting shown **commented out** at its default, and a comment above each saying what it does (`SETTINGS_TEMPLATE` in `settings-file.ts`; a test holds the shown defaults equal to the code's). Nothing in it is in effect until you remove a `#`, so a setting you leave alone keeps following toriel's current default when an upgrade changes it. It never touches an existing file. An old `settings.json` is still read while there is no `settings.yaml`; `toriel doctor --fix` converts it (only the keys you had set become active lines, inside the commented template; the old file is set aside as `settings.json.bak-<time>`). Code that edits the file goes through `updateSettings` (`settings-file.ts`), which keeps the comments. All keys optional: `steeringMode` (`"all"`, the default, or
`"one-at-a-time"`), `provider`, `model`, `thinking`, `piCli`, `warnNoPermissionSystem` (boolean, default true: see "Resources audit"), `scheduleUsagePause` (percent, default 95, 0 = never: scheduled runs wait while a usage window of the session's provider is at or above it), `scheduleDailyLimit` (default 200 scheduled runs per 24 hours across all sessions; read when the daemon starts), `preventSleep` (boolean, default true: see "Scheduled prompts"), `showExternalSessions` (boolean, default false: list sessions toriel never ran in the switcher; `/external` flips it for one run), `fileFreshness` (boolean, default true: refuse an edit or write of a file the session has not read or that changed since; ## Messages between sessions

`toriel_message({to, text})` (pi extension `pi/extensions/toriel-agents.ts`, children only) asks the daemon (`message` command, `daemon-handlers-messages.ts`) to deliver `text` to `to`: a UUID, UUID prefix, `#number` or name (`daemon-resolve.ts` finds it, in the daemon's sessions first, then session files on disk). The target gets a message `[from NAME (uuid)]: text` (`received.ts`); an inactive session is started for it; a compacting one holds it with the other held messages. When the target has the session bridge extension connected (`daemon-handlers-bridge.ts`), the daemon hands the message to the bridge (`bridge_inject`) and the extension delivers it as a `toriel-inject` custom message at a turn/settle boundary or immediately when idle - confirmed by the append, never pi's steering queue; otherwise it is queued as legacy steering (`deliverToSession`, which warns once when the bridge is missing). Delivering does not take the target's input attach. Refused: unknown or ambiguous target, itself, a session open in another pi process, empty text. The caller gets "delivered", not a reply; a reply is a message the other way. Received messages are shown as "from NAME" and are not offered as rewind points.

## Subagents

`toriel_agent({agent, task, description, model?, background?, context?, system?, cwd?})` and `toriel_agents({action, id?, timeoutSeconds?})` (pi extension `toriel-agents.ts`) let a session delegate a task to a subagent: a real pi session the daemon starts (`daemon-subagents.ts`, limits and records in `subagents.ts`) with the named agent profile, recorded in `lineage.json` as `kind: "subagent"` so it nests under the caller. The daemon sets `TORIEL_CAN_SPAWN=1` and `TORIEL_AGENT_TYPES` (the profiles visible from the session's directory) in the child's environment; the extension registers the tools only then, and the description lists the live types. The daemon also leaves `+toriel_agent,+toriel_agents` out of `--tools` for sessions that may not spawn.

- **Foreground (default).** The call holds one request open on the daemon socket until the subagent settles, then returns its final assistant text; several calls in one turn run in parallel. The request carries no timeout of its own and holds no pi RPC open (the daemon only waits for the child's `agent_settled`), so a long run does not hit the RPC timeout `compact-wait.ts` works around (the watchdog below is the only clock). Cancelling the call (the extension drops the connection) or stopping the parent's process stops the subagent.
- **Moving a foreground call to the background (ticket 212).** `ctrl-b` (or `/background`) while the agent waits for foreground subagents lets go of every such call: each answers at once with text saying the user moved it, the record becomes a background one (so the background time limit now applies), and its result arrives later as a message like any background result. The time limit counts from when the subagent started, so one moved just before it has run that long is stopped almost at once. The first press moves subagents; with none waiting it moves a bash command as before. The daemon releases the call through `SubagentManager.backgroundForeground`; a press while the subagent is still starting is remembered and applied the moment the call waits.
- **Background.** `background: true` answers at once with a handle (`#N`); when the subagent ends, the daemon delivers `Subagent #N (...) finished` plus its result to the parent as a message (the `toriel_message` path; an idle parent is started). A background subagent outlives its parent's turn and process.
- **`toriel_agents`.** `list`, `status`, `result` (by `#N`), `wait` (an id, or all running ones; `timeoutSeconds`, default 300) and `stop`. Only the session that started a subagent can see or stop it.
- **Agent types** are the profiles in `agents/` (see `agents/README.md` "Shipped types") plus your own; the `delegating` skill tells a session when to use them. Delegating never widens what a session may do: a subagent that edits asks for permission like its parent.
- **`context: fork`** starts the subagent from a copy of the caller's conversation (the `/fork` path); `model` cannot be changed then. `system` is appended to the profile's prompt after a short note naming the parent.
- **`cwd`** runs the subagent in another directory than the parent's (agent profiles are still found relative to the parent's cwd). The child is write-scoped to that cwd, so a linked-worktree worker's writes inside it are silent and outside it denied - while a cwd that is not a linked-worktree root gets ask mode, so outside-root writes are forwarded to the dialog, not denied. The daemon validates the path before starting the child: it must be absolute, an existing directory, and inside the parent's cwd (after symlinks) or a worktree of the same repository (the rule is symmetric: a parent in a worktree may spawn into the main checkout or a sibling worktree; recognized by the cwd's .git entry, so the worktree's root, not a subdirectory of it) - a child's scope root is its cwd, so a child elsewhere would get silent writes there, and delegating never widens what a session may do.
- **Seeded grants.** A subagent starts with read-only git/gh grants and a copy of its parent's active grants (see `docs/permissions.md` "Seeded grants"), so worktree work does not prompt on reads.
- **Limits** (`DEFAULT_SUBAGENT_LIMITS`; the `subagent*` settings change them, read when the daemon starts): depth 1 (`maxDepth`, never above 2), 3 running at once daemon-wide, 20 spawns per parent, 150000 tokens per subagent unless the profile's `budget` says otherwise, capped by what a subagent parent has left; the profile's `maxTurns` and `canSpawn` apply. A refusal comes back as the tool's text. Since only sessions below `maxDepth` get the tools, the hard cap of 2 is reachable only by raising `maxDepth`.
- **A death says how.** A subagent whose process exits on its own is `failed` with `its process exited (code 1)` or `(signal SIGKILL)` plus a 200-character stderr tail with key/token/password pairs and bearer tokens scrubbed (`subagent-exit.ts`; the full stderr stays in the daemon log); a deliberate stop stays `stopped`. An abort carries pi's error text when there is one, else `aborted mid-run; no stop was requested`. The line that opens a delivered result carries the short reason: `failed (its process exited (code 1))`, `was cut short (its parent cancelled the call)`.
- **The budget is visible.** While you view a subagent, the status line reads `SUBAGENT of X | budget 38.0k/150.0k, turn 7/25` (the turn part only when its profile sets `maxTurns`), drawn as a warning from 80% of the tokens or turns; a running subagent's row in the switcher leads its description with the same figure; `toriel_agents list` shows `tokens/budget` and `turns/maxTurns` to the parent. The daemon broadcasts the session list after every assistant message so it moves while the subagent works (`SessionMeta.subagent`, `subagent-budget.ts`). It is the budget's own count, not the larger session total elsewhere in the status bar.
- **Budget and turns** are counted from the child's own `message_end` events (`SubagentRecord.tokens`): fresh input, output and cache writes of each assistant message, not cache reads (pi's `totalTokens` re-counts the whole cached context every turn, which made a run that only ever held ~25k tokens of context "use" 150k in seven turns). A subagent whose message ends in a tool call is aborted once it is over budget or at `maxTurns`; the parent gets the partial text and the reason (state `limit`). A subagent that ends any other abnormal way is also reported, never as a plain "done": a run that settles on an abort (esc on its view, `/abort`) comes back as `stopped` ("was interrupted (aborted) before it finished"), one that settles on an error as `failed` with the error text, and when its last message is empty the newest non-empty assistant text is returned as the partial result. A stop the daemon asked for (limit, cancel, `toriel_agents stop`) wins over the settle its abort causes.
- **When it ends** the daemon picks the result text from the subagent's transcript: the newest non-empty assistant text - unless a custom injection or background-job notice sits between it and a previous text at least twice as long (a worker answering a late notice after posting its report would otherwise bury the report under the acknowledgment), in which case the previous text wins; it then stops the process and keeps the session file, so the subagent shows as a parked child that can be opened.
- **A stuck subagent is stopped.** The turn and token limits fire only when an assistant message ends, so a run wedged inside one tool call never reaches them (ticket 159: frozen 11 minutes in a single `npm` call). The daemon keeps `lastEventAt` per running subagent, refreshed by every event its process emits, and `SubagentManager.checkWatchdog` (a timer, a quarter of the shorter limit, at most every 30 s) stops one that has been silent for `subagentIdleMinutes` (default 15, `0` = never; `TORIEL_SUBAGENT_IDLE_MS` wins). A permission prompt waiting for an answer is not silence: while a subagent's dialog is open its clock keeps restarting, so the limit counts from the answer. `subagentMaxMinutes` (default 0 = no cap; `TORIEL_SUBAGENT_MAX_MS` wins) adds a wall-clock cap for *background* subagents only, since a foreground caller can stop its own. The stop goes through the ordinary path: the partial result is kept, the parent is told `stopped: it produced nothing for 15 min (stuck in a tool call?)`, state `stopped`. A tool that runs silently for longer than the idle limit (a 20-minute build that prints nothing) is cut too: raise the setting for that kind of work, or have the agent run it with `run_in_background` and poll.
- **Finished subagents grey out, then go away.** Once a subagent has ended and its parent has the result (a foreground call answered, or a background result delivered) its switcher row is dimmed (`SessionMeta.subagent`, `SwitcherSession.finished`); a subagent that is stopped on disk after a daemon restart is dimmed too. 30 minutes after that (`subagentKeepMinutes` in the settings; `TORIEL_SUBAGENT_KEEP_MS` overrides it, mainly for tests) the daemon deletes it the way `/delete` does: the file goes to the trash (`/restore` brings it back as a top-level session, because the lineage link is cut), and the row leaves the list. The sweep (`SubagentManager.sweep`, every 30 s and at start) works from `lineage.json` and file times, so it also catches subagents that finished before a restart; it never touches one that is running, has a live process, or was written to since the window began. The in-memory record outlives the session, so `toriel_agents result` still returns the text. The daemon cannot tell which session a controller is merely viewing, so a swept subagent can be open on screen: its next prompt says "that session was deleted - /restore brings it back from the trash" (the controller notices the file is gone; the daemon refuses a prompt by file too, for the race where the controller still lists it) instead of starting a ghost, and `/restore` brings it back. The trash move falls back to copy-and-delete when the trash and the session files are on different filesystems (an isolated instance's tmpfs runtime dir), so `/delete` and the sweep work there too.
- **Permission dialogs trickle up.** A dialog raised in a subagent is shown in its parent's view, labelled `Subagent N 'name'` (the same panel, keys and grant rows; `dialog-route.ts` picks which view's dialog is on screen, the parent's own first), and the answer goes back to the subagent without attaching to it. The parent's row, folded or not, gets the attention marker and "N waiting on permission". Nothing is denied automatically: with no controller attached the dialog stays pending (badge on the subagent, blocking only it) and is shown to the next controller that connects. "Allow for ..." rows store the grant for the subagent's own session. Only the subagent's direct parent shows it. Profiles default to read-only tools, so most subagents never ask.
- **Records live in daemon memory.** Handles, spawn counts and results are lost when the daemon restarts (the session files and the lineage stay); a restart also ends running subagents.

## Bundled pi packages (ticket 230)

Third-party pi packages every environment wants are dependencies of toriel (pinned exactly in `package.json`: `@juicesharp/rpiv-ask-user-question`, `pi-web-access`, `@gotgenes/pi-permission-system`, `pi-hermes-memory`), so `npm install` is the only install step. `src/bundled-packages.ts` lists them (`BUNDLED_PACKAGES`: name, what it gives, the tools it registers, whether only plain sessions get it) and decides per session which load.

- **How.** Each is passed to the pi child as `-e <toriel>/node_modules/<package>`. pi loads a package directory by its manifest, and an explicit `-e` loads under `--no-extensions` too (checked on pi 1.4.0 for all three, without the optional `@juicesharp/rpiv-i18n`). The package's own configuration and state stay where it keeps them in pi's config directory (`web-search.json`, hermes' memory store), so they are per machine as before. Their tool names are added to the child's `--tools` list (`+name`) so a resumed session offers them too.
- **Never twice.** pi refuses to start a session when two copies register the same tool (`Tool "x" conflicts with ...`). A package listed in pi's `settings.json` `packages`, or in the project's own `<cwd>/.pi/settings.json` (what `pi install -l` writes; `projectPackageListed`, read even when the project is untrusted, since leaving toriel's copy out is the safe side), is the user's own and wins: toriel leaves its copy out (`packageState` "user"). The toriel setting `bundledPackagesOff` (a list of names) leaves any of them out of every session ("off").
- **Which sessions.** A plain session loads all of them. A profile without a tool list gets the ones that are not the user's own state (not hermes-memory, so a subagent never writes your memory), unless it is `minimal`. A profile that owns its tool list loads a package only when it names one of its tools (the shipped research-web agent names `web_search`). The exception is the permission gate (`always: true` in `BUNDLED_PACKAGES`): every session loads it, minimal and tool-listing profiles included, since a session without it has nothing that asks. It registers no tools, so it adds nothing to `--tools`.
- **The permission gate's doctor check.** `permission-package` counts the package as installed when it is bundled (or the user's own copy is in pi's settings) and says so when `bundledPackagesOff` switches it off or `npm install` did not run. Its config (`~/.pi/agent/extensions/pi-permission-system/config.json`) is unchanged and still the user's to write. `test/pi-smoke.test.ts` loads the bundled copy into the pinned pi.
- **Doctor.** `bundled-packages` reports a package that is neither in `node_modules` (npm install did not run), nor the user's own, nor switched off. `web-package` (the agents that need web tools) now fails only when the package is off or missing, and says which.
- **Updating (ticket 75).** `toriel update [status]` reports what is installed against what npm has (`src/updates.ts`, `src/update-cli.ts`): pi (toriel's own `node_modules` copy, `pi-coding-agent` and `pi-tui` together; a global `pi` on PATH is never used), each bundled package, and the user's own pi packages from `settings.json` (their installed version is read from `npm root -g`). A bundled package the user also lists is marked SHADOWED, with the version of theirs that actually runs. npm is asked only on request, never at startup; the answers are cached for a day in `$XDG_CACHE_HOME/toriel/updates.json` (`--refresh` asks again). `toriel update all|<name>...` bumps toriel's own (`npm install --save-exact`, then `npm run typecheck` and `npm test`); a failure puts `package.json` and the lockfile back and runs `npm ci`. It never touches the user's own packages (`pi update` does) and never a running session: restart toriel afterwards (`toriel kill-server`). `test/pi-smoke.test.ts` runs the real pinned pi (version equals the pin, `--tools` refuses a mix of bare and `+name` entries, RPC `get_state` answers with a `sessionId`) so a bump that breaks an assumption fails there first. A stub model endpoint scripts a todo_write, three reads and the text of the continued turn, so one test runs a real tool-call cycle with no network and checks the extension events the task reminders (ticket 250) ride on: `before_agent_start` fires once per user prompt, `tool_result` and `agent_before_settle` as toriel assumes, and a boundary's `continue: true` buys exactly one turn while pi re-emits `agent_start` for it. A bump is an ordinary dependency bump in toriel, checked by its suite. The permission system (`@gotgenes/pi-permission-system`) is bundled like the others (ticket 230 stage 4, after the local patch to it was retired, ticket 223), but it is the permission gate, so a bump of it deserves a read of its changelog before the suite's word: it must keep its authorizer seam (`registerAuthorizer`, `permissions:ready`), `checkPermission` and the dialog titles toriel matches (`docs/permissions.md`). `TORIEL_BUNDLED_ROOT` points the lookup elsewhere (the tests use it).

## Plan mode (ticket 229)

`/plan [on|off|status]` (no argument toggles; `plan_mode`, protocol 12; `handlePlanMode`) puts a session in a mode where the agent can only look: it explores, writes a plan and calls `exit_plan_mode`; you approve it, ask for changes or reject it. The agent can ask for the mode itself with `enter_plan_mode` (that only takes power away, so it needs no approval); only an approval, or `/plan off`, ends it. The status line shows `PLAN MODE`, and each flip is a durable notice.

- **State.** One marker file per session, named by the session's UUID, in `TORIEL_PLAN_DIR` (default `<state>/plan-mode`, mode 0700; `pi/extensions/lib/plan-mode.ts`). The daemon writes it for `/plan`; the `toriel-plan` extension writes it for `enter_plan_mode` and an approval, and reads it at every tool call and every bash launch, so a flip takes effect on the next call with nothing restarted, and the mode survives a restart of the child or the daemon. The extension reports each flip and each session start to the daemon as a `setStatus` record under `toriel-plan` (`{v: 1, on}`; for the daemon, never shown), which keeps `SessionMeta.plan` right.
- **What is blocked.** `toriel-plan.ts` hooks `tool_call` and refuses, with a reason the model reads, every tool that is not on the read-only list (`PLAN_TOOLS`: read, grep, find, ls, bash, codemode, tool_search, the web tools, `toriel_usage`, `toriel_job`, `toriel_schedule_list`, `toriel_agents`, `toriel_permission_check`, `todo_write`, `ask_user_question` and the two plan tools). `write` and `edit` are therefore refused, and so are `toriel_agent` (a subagent is not in plan mode), `toriel_message`, `toriel_schedule_create`, `toriel_watch_create` and any tool it does not know. An MCP tool (`mcp__<server>__<tool>`) runs only when its server has `readOnly: true` in `mcp.yaml`, read at the moment of the call; codemode's inner calls come through the same gate one by one.
- **Bash.** `toriel-jobs.ts` asks `planOn` at every launch: in plan mode the command runs in bubblewrap with the whole filesystem read-only, nothing writable, a private `/dev`, `/proc` and `/tmp`, the socket directories emptied and the daemon's socket hidden (`planWrap`, the sandbox's `bwrapArgs` with no writable root; the network is left alone, planning may read the web). It applies to every session, scoped or not, and no list of "safe commands" has to be guessed. Without bubblewrap the command is not run, and the error says why.
- **The plan.** `exit_plan_mode({plan})` shows the plan as a select dialog (`Approve the plan and start`, `Keep planning`, `Reject the plan`) through the normal dialog relay, so it appears in the parent's view for a subagent and obeys deny-after (an unanswered one is dismissed, which counts as not approved). `Keep planning` asks for the changes in a line of text and hands it to the agent. A dialog is never taken for a permission prompt, so auto mode and grants never answer it.
- **What the agent is told.** `before_agent_start` adds a short note with each user prompt while the mode is on (`PLAN_ON_NOTE`), and one note when it has ended, so the model knows without a message between the processes.
- **What it is not.** A guardrail for an agent that follows instructions, not a boundary against one that does not (the permission rules, the scope root and the sandbox are the boundaries; a marker file can be removed by anything that can write the state directory, and the read-only mount keeps bash from doing it). A plan is not kept apart from the conversation: it is the `exit_plan_mode` call and its result, so a compaction can summarize it away. Starting a spawned agent in plan mode is not built.

## The agent's task list (ticket 228)

An agent working on something with several steps keeps a list with the `todo_write` tool (`pi/extensions/toriel-tasks.ts`, pure half `pi/extensions/lib/tasks.ts`). Each call sends the whole list (`[{content, status, activeForm?}]`, status `pending`, `in_progress` or `completed`; at most 50 tasks; an empty list clears it), so the list is the last call. It is stored in that call's tool result (`details`) and read back from the session branch (`reconstructTodos`), which is why a fork, a rewind and a resume each show the list as it stood at that point; nothing is kept outside the session file. A wrong call (bad status, empty content) changes nothing and tells the agent why. The answer to a good call nudges when no task, or more than one, is `in_progress`.

The extension reports every change, and every session start and tree change, to the daemon as a `setStatus` record under `toriel-tasks` (`{v: 1, todos}`; like the usage record it is for the daemon and never reaches a controller, `takeTasksReport`). The daemon keeps it on the live session (`DaemonSession.tasks`, memory only) and puts it in the session list as `SessionMeta.tasks`. The controller draws it above the editor, over the schedule lines (`stripLines`: `tasks 1/3 done`, the task under way by its `activeForm` in the accent colour, then what is next, six lines at most with `+N more`; a finished list is the header alone), and `/tasks` opens the whole list in the info panel. The user cannot edit the list: the agent owns it.

**Reminders (ticket 250).** Models write a list and then forget to update it (marking work done has no immediate payoff), so the extension reminds them from outside, like Claude Code (`pi/extensions/lib/task-nudge.ts`, pure state). While items are open and `todo_write` has not been called for 8 tool calls, the next tool result gets a line appended ("your task list (0 of 6 done) still shows "Reading the diff" in progress, 5 more open. If that has changed, update it now..."), and again every 8 calls; a list that is empty or fully done is never mentioned, and any `todo_write` (or a session start, resume, fork or rewind, which read the list back) starts the count again. When a run is about to end (pi's `agent_before_settle`) with items open and at least 3 tool calls since the last write, the extension adds a hidden custom message with the same text and asks for one more turn, once per run (an abort never does), so "all done, list still open" gets recorded. The constants are `MID_RUN_CALLS` and `END_OF_RUN_CALLS`.

**A stale list (ticket 251).** Whatever the reminders achieve, the strip should not look current when it is not. While a session is working and its list has open items, the daemon puts `SessionMeta.tasksStaleSince` in the session list: the later of the list's last report and the start of the current run (`DaemonSession.tasksAt`, `runSince`; memory only), so an hour-old list does not read as stale ten seconds into a new run, and an idle session or a finished list never does. Once the controller sees five minutes of that (`STALE_AFTER_MS`) the strip's header says `tasks 0/6 done - not updated 12m`, the in-progress line loses its accent colour, and `/tasks` carries the same note; the next report clears it.

## Scheduled prompts

`/in 90m <prompt>` (once, after a delay), `/at 14:30 <prompt>` (once, at a clock time; `tomorrow 9am`, `fri 17:00`, `2026-12-25 08:00`), `/every 30m <prompt>` or `/every weekday 9am <prompt>`, `/loop [5m] <prompt>` (runs now, then again after each run finishes; with no gap the prompt carries a footer telling the agent to schedule the next pass itself with `toriel_schedule_create`, and the loop ends when it does not) and `/cron "*/15 * * * *" <prompt>` put a timed prompt into the session you are viewing. `/schedules` lists them with the real next run (`--all`: every session's; in the switcher it always lists all), `/cancel`, `/pause`, `/resume` take an id (`3` or `#3`) or a name (`--all` for everything in scope), `/fire <id>` runs one now. Flags: `--name`, `--max N`, `--expires 3d|never`, `--catchup once|skip`, `--dry-run` (print the next fire times, create nothing), and on the repeating commands `--until <shell command>` / `--while <shell command>` (the daemon runs the command in the session's directory before each run, no model involved: `--until` succeeding sends the prompt one last time and ends the schedule, `--while` failing ends it quietly, a check that cannot run or times out after 30 s just waits; the shortest interval with a check is 10 s instead of 1 min; the agent tools deliberately have no such option, since a shell command there would sidestep the permission dialogs). Each command echoes how it read the time, with the real next run and the expiry.

The daemon owns the clock (`scheduler.ts`, state in `schedules.json`, `TORIEL_SCHEDULES` overrides), so schedules fire with no controller attached and survive restarts. A fire is delivered the way a message from another session is (`deliverToTarget`), labelled `[scheduled #3 "name", run 4/20]: prompt`, which the transcript shows as a scheduled prompt and rewind skips. It starts a stopped session, never interrupts: a busy, compacting or dialog-showing session is checked again when it settles (at least every 5 s), and missed fires are dropped, not stacked. After daemon downtime a schedule fires once, flagged late (`--catchup skip` just moves on; a one-shot always fires). Repeating schedules expire after 7 days unless `--expires` says otherwise; the shortest interval is 1 minute, at most 20 schedules per session. Five failed deliveries pause a schedule (`/resume` clears it). Two guards hold a due schedule back (it waits, says why once in its session, and `/schedules` shows `waiting: ...`; it runs, flagged late, when the hold lifts): the daily limit (`scheduleDailyLimit`, counted across sessions and kept across restarts) and the usage budget (`scheduleUsagePause`, from the same reports as the status bar's usage). A strip above the input lists the viewed session's active schedules (three at most, soonest first, fixed clock times). While any session has a turn running, or an active schedule is due within 30 minutes, the daemon holds a logind inhibitor lock (`sleep-inhibit.ts`: a `systemd-inhibit --what=idle:sleep` child that also exits when the daemon's pid goes away; Linux only; `preventSleep: false` turns it off; `TORIEL_NO_INHIBIT=1` does too, for tests) so the machine does not suspend with work pending. Deleting a session removes its schedules; stopping it does not. The session list shows `@14:05` (and `x3` for several) after a name, and the status line `sched 2, next 14:05 (in 12m)`; a schedule that ends or fails says so in its session. Agents schedule themselves with `toriel_schedule_create({when, prompt, name?, max?, expires?})` (`when` is the same string the commands take, e.g. "in 30m", "every weekday 9am"), `toriel_schedule_list` and `toriel_schedule_cancel({id})`, always within their own session and marked as agent-made (tighter cap: 10); the `scheduling` skill says when to use them. Time parsing is `when.ts` (hand-written, local time; cron through the `cron-parser` package). Design and what is still to come (a `/schedules` picker with row actions): docs/design.md item 10.

## File triggers

`/watch [--name n] [--once] [--on write|any] [--cooldown 5s] [--expires 3d] <path> <prompt...>` sends the prompt into the session when a file changes, instead of at a time ("when `/tmp/permissions.review.md` appears, read it" - instant and free, where a 30-minute poll timer was neither). It is a schedule whose trigger is a file change (`Trigger` kind `watch`, `when.ts`), so it is created by the same `Scheduler` and everything above applies: it waits for an idle session and never interrupts a turn or a permission prompt, starts a stopped session, counts against the per-session cap and the daily run limit, expires after 7 days unless `--expires` says otherwise (`never` works), pauses itself after five failed deliveries, shows in `/schedules` (as `on change: <path>`, `watching` while it waits) and is paused, resumed, fired (`/fire` runs it now) and cancelled like any schedule. `--once` is `--max 1`.

- **What counts as a change.** A directory is watched as a directory (anything directly inside it; not recursive: inotify watches are a shared, limited resource); anything else is a file, which need not exist yet but whose directory must. `--on write` (the default) is a create or a modification; `--on any` also counts a delete or a rename away. A relative path is relative to the session's directory; `~` works. A path on a special filesystem (`/proc`, `/sys`) arms but delivers nothing - inotify accepts it and those filesystems never produce events - so it sits showing `watching` forever; cancel it if you made one by mistake.
- **One save is one prompt.** A save is several inotify events, and most editors save by writing a temp file and renaming it over the target (which a watch on the file itself would miss), so a file is watched through its parent directory and filtered by name, and the trigger fires after `--cooldown` of quiet (default 2s, between 1s and 10m; watchman's term). A burst that never goes quiet still fires once a minute. While the session is busy, any number of changes make one pending fire, like a missed schedule slot; a change that arrives while the prompt is being delivered is a new fire.
- **What the agent gets.** The ordinary scheduled-prompt label, and a first line naming the file (`(File trigger: /path changed.)`). The file's content is not included; the agent reads it.
- **Live only.** inotify does not wake a sleeping machine and does not replay: a change while the machine sleeps or the daemon is down is lost, except a fire that was already pending when the daemon stopped, which is delivered after the restart like a late schedule. The daemon keeps one watch per active watch schedule (`daemon-watch.ts`, at most 50), re-arms them when it starts, stops watching a paused or ended one at once, and checks every 30s that a watched directory is still the same directory (a deleted and recreated directory silently stops delivering). A watch that cannot start (its directory is missing, a system limit) is not dropped: `/schedules` shows `waiting: cannot watch (...)` and it is retried every 30s.
- **Trust.** Anyone who can write the watched file can steer the session with what it says, exactly as with anything the agent reads; watch paths you trust. **An agent may make one too** (`toriel_watch_create`, ticket 191; the `watch_add` command with `by: "agent"`, protocol 9), under tighter limits because an agent watching a churning directory is a spam risk schedules do not have: the quiet time is at least 30s (and 30s by default), it must end by itself (`once`, or `expires` of at most 24h; `never` and longer are refused), a session may have 3 of them (and 10 agent-made schedules of all kinds), and the scheduler pauses one that has fired 6 times within an hour after delivering that sixth prompt with a note saying so (`agentWatchFiresPerHour` in `scheduler.ts`; a `/resume` starts the hour again; the hour's fire times are in memory, so a daemon restart also resets it). A person's own `/watch` keeps the ordinary limits.
- Code: `file-watch.ts` (the watcher: debounce, atomic saves, directory replacement; node's `fs.watch`, no dependency), `daemon-watch.ts` (keeps the watches in line with the schedules and calls `Scheduler.triggered`), `watch-path.ts` (path resolution), the `watch_add` command (protocol 4). Not yet: recursive watches or globs, a catch-up check on resume.

## Background commands

The agent can start a shell command and carry on: `bash({command, run_in_background: true})` returns a job id at once, and when the command exits the agent gets a message (`Background job j1 (npm run build) exited with code 0 after 4m12s`, with the last lines of output) that wakes an idle session like a scheduled prompt does. `toriel_job({action: "list" | "output" | "stop", id?, since?})` lists the session's jobs, reads output (the last 8000 bytes, or from byte `since`; each read says where to continue) and stops a job. The code is `pi/extensions/toriel-jobs.ts` (children only; plain pi keeps its own `bash`).

- **Permissions are unchanged.** The extension replaces pi's `bash` with a tool of the same name, so every pi-permission-system `bash` rule (`git *: deny`, `sudo *: ask`, ...) and every grant applies to a background command exactly as to a foreground one, and nothing needs configuring. A foreground call is delegated to pi's own bash tool untouched. A profile whose `tools:` list leaves out `bash` does not gain it.
- **Ownership.** A job is a detached process group owned by the session's pi process. It is killed (SIGKILL, no notice) when the session shuts down, so `/stop`, deleting the session and `toriel kill-server` leave no jobs behind; a pi that crashes or is SIGKILLed can leave one running, and then nothing enforces its 2-hour cap or reports its exit. Stopping on request sends SIGTERM to the group, then SIGKILL after 3 s, and gives no exit notice (the agent asked).
- **Limits.** 5 running jobs per session (starting a sixth is refused with a message), 2 hours of lifetime (then the job is stopped and the agent told), 8 MiB of log per job (the rest is dropped, with a marker). Output goes to a temp directory that is deleted at shutdown.
- **Environment.** A job gets what pi's own bash tool gives a foreground command: pi's bin directory first on `PATH` (so `rg` and `fd` work), and the session variables `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, `PI_REASONING_LEVEL`. pi's `commandPrefix` and `shellPath` settings are not applied to background jobs.
- **Moving a running command to the background (#8).** While the agent waits for a `bash` call, `ctrl-b` (or `/background`) turns it into a job: the call returns at once with the output so far plus a note ("The user moved this command to the background as job j2 ..."), the process keeps running, and the exit notice and `toriel_job` work as for any job. Every foreground command of that session moves (parallel calls included); one past the 5-job limit stays where it is and the notice says so. `ctrl-b` only acts while the agent is working; otherwise it is the editor's cursor-left. The mechanism: the extension gives pi's bash tool its own `operations.exec`, so a foreground command is a process in the same registry (invisible until moved: no id, no listing, no notice, not counted against the 5-job limit), and the daemon reaches it with the extension command `/toriel-background` over the child's RPC pipe (`background` request, `handleBackground`; a child without the command is refused with a message instead of being sent the text). Differences from pi's own foreground runner: `shellPath` is not honoured (plain `bash`), a `timeout` stops applying once a command is moved (the 2-hour job cap takes over), and the command's output goes to the log from then on. A `!command` cannot be moved (esc stops it).
- Not yet: `/jobs`, and a status segment. Design notes: docs/design.md "Background commands".

## Command sandbox

On by default since 2026-11-15 (`"sandbox": "bwrap"`; `"sandbox": "off"` in the toriel settings turns it off; the owner had run it for days first). Without bubblewrap that really runs, every `bash` command of a scoped session is refused (it never runs unsandboxed), and `toriel doctor` says so. Every `bash` command (foreground or background) of a **directory-scoped** session (any agent-profile session; see `TORIEL_SCOPE_ROOT`) runs inside [bubblewrap](https://github.com/containers/bubblewrap): the whole filesystem is read-only except the places below, so a program the agent runs (`npm run`, `make`, `find -exec`, an interpreter) cannot write where the scope link would have stopped pi's own write tool. Unscoped sessions and `!command` are never sandboxed. The setting is read when a session starts. The findings behind the design, with the probes that back each claim, are in docs/sandbox-spike.md.

- **Writable:** the scope root; the resolved target of a `node_modules` symlink that leaves it (a toriel worktree links `node_modules` to the main checkout, and writes through a symlink land on the target); in a linked worktree, only what `git commit` needs of the shared git directory (the worktree's own git dir, and `objects/`, `refs/heads/`, `logs/`); the shared directory `~/.local/share/toriel/shared` (`$TORIEL_SHARED_DIR`: the stable place to hand files between agents or to you; created by the daemon, mode 0700); and the `sandboxWritable` roots (default `~/.npm` and `~/.cache`, so package installs work; `[]` for none). Everything else, including your home, is read-only and a write fails with "Read-only file system".
- **Kept read-only inside those:** an existing `<root>/.pi` (pi's project configuration, including the permission policy a trusted project layers over yours; ticket 223, see "The scope veto"). A command can never plant something your own `git` will later run outside the sandbox. In an ordinary checkout `.git/hooks` and `.git/config` are carved out; in a linked worktree the `.git` pointer file, the git dir's `commondir`/`gitdir` files, `config.worktree` and the shared `hooks/` and `config` are (rewriting a pointer would aim the host's git at a directory the agent controls). Binding the whole shared git directory would allow all of that, which is why it is not done.
- **Live sockets are hidden.** A read-only bind does not stop a command connecting to a unix socket, and a connection is as good as a write: through the session D-Bus a command can start anything outside the sandbox, and through the daemon's socket it can talk to toriel itself (answer permission dialogs, start sessions). So `/run/user` (the session bus, wayland, pipewire, and the default daemon socket) and `/run/dbus` are replaced by empty directories, and `/dev/null` is bound over `TORIEL_SOCK` wherever it lives. Tested with a real socket (the test has controls: it answers outside the sandbox and inside without the hiding).
- **`/tmp` is the sandbox's own, persistent one (ticket 204); `/dev` and `/proc` are private per command.** The real `/tmp` holds live sockets (tmux, X11, ...) that a sandboxed command could connect to and act through, outside the sandbox, so it is never bound. Instead `~/.local/share/toriel/tmp` (`TORIEL_SANDBOX_TMP_DIR` overrides it; created by the daemon, mode 0700, handed to the child as `$TORIEL_SANDBOX_TMP`) is bound over `/tmp`: files written there survive from one command to the next, and from one session to the next, and **all sandboxed sessions share it**, so a subagent that is restarted (or its parent) finds the scratch files it left. The cost of sharing is name collisions between unrelated sessions (`/tmp/out.txt`); the bash tool's description tells agents to name files distinctively. Nothing cleans it up (delete the directory's contents when it grows). If the directory is missing at launch the command still runs, with an empty `/tmp` per command as before. `/var/tmp` is under the read-only root, so tests that build trees there fail with EROFS in a sandbox. A scope root under `/tmp` is refused (the sandbox's `/tmp` is not the host's, so the root would not be there).
- **Fails closed.** The sandbox is applied per command: the wrapper (`pi/extensions/lib/sandbox.ts`, wired in at the one spawn in `toriel-jobs.ts`) recomputes the policy at every launch. If the setting is on but the sandbox cannot be applied (bwrap missing or unusable, an unusable scope root), the command is refused with the reason and is never run unsandboxed. The doctor checks that bwrap really runs (feature level, only when the setting is on). A scope root that is itself a symlink is also refused (it is not canonical; the same rule the scope link applies), so a session launched through a symlinked directory refuses every sandboxed command until it is launched from the real path.
- **Git inside the sandbox has rough edges worth knowing.** `git commit` works but may print `Unable to create '.git/packed-refs.lock': Read-only file system` while still succeeding (loose refs are writable; repacking the packed-refs file is not, and git degrades gracefully). Operations that repack or download refs - `git gc`, `git pack-refs`, `git fetch`, `git pull` - fail read-only, which is consistent with the seeded read-only grant set. And because executing a read-only-mounted file is allowed, `GIT_CONFIG_GLOBAL=<file in the worktree> git commit` makes git run a `hooksPath` hook from the worktree - inside the sandbox, where it can only reach what the command can; the host's git never sees that config.
- **What it does not do.** pi's own read/write/edit tools are not inside it (the scope link guards them, and a config allow still short-circuits that); reads are not jailed; MCP servers pi starts are separate processes; a running process's sandbox cannot be widened (neither bwrap nor landlock can), so a path approved later applies to the next command, not to a background job already running. Network access is NOT cut, on purpose: some agents need it (`npm install`, `curl`; the `web_search` and `fetch_content` tools run inside pi, not through bash, and are unaffected either way). bwrap can cut it per command (`--unshare-net`), which is the intended opt-in for agents that do not need it (a profile key, not built yet). The price of leaving it on: abstract-namespace unix sockets (the X server's and D-Bus's abstract sockets) are only hidden by a separate network namespace, so a sandboxed command can still reach them while the network is on. In an ordinary checkout the scope root contains `.git/worktrees/`, so a command there can still rewrite the pointer files of that repository's other linked worktrees (the carve-outs above protect the checkout's own `hooks` and `config` only). The sandbox keeps the host's pid namespace, so `/proc` shows the host's processes; reading or writing another process's memory or `/proc/<pid>/root` is refused by the kernel's Yama ptrace restrictions (`ptrace_scope=1`, the Fedora default) - on a host with `ptrace_scope=0` those paths would be more open.
- **Not yet:** a way to approve an extra writable path for a session while it runs (the policy function already takes approved paths and the wrapper applies them on the next command; no command or dialog feeds it yet), the read jail (board 167), and sandboxing the pi process itself.

## File tools: freshness, edit hints and replaceAll (ticket 63)

`pi/extensions/toriel-files.ts` (children only) improves pi's read/write/edit tools without replacing how they read or write. The study of pi's tools against Claude Code's (ticket 63) found pi's tools already cheap and robust (multi-edit calls, fuzzy matching of quotes and dashes, BOM and CRLF kept, streamed reads with an `offset=` continuation hint); the gaps were these three.

- **Freshness** (`lib/freshness.ts`). The extension remembers every file the session read, wrote or edited (path by real path, mtime and size, plus a content hash up to 2 MB). An `edit` or `write` of an existing file the session never read, or whose mtime and size changed since, is blocked (a `tool_call` block, like the scope veto) with an error telling the model to read it first or again. A file that does not exist is new and is never checked; a touch that left the bytes alone is not a change; the session's own successful write or edit counts as a read. A command (`sed -i`, a build) that changed the file counts as a change. The record lives in memory, so a resumed session must read again. On by default; the `fileFreshness` setting (false) turns it off for sessions started after the change.
- **Edit hints** (`lib/edit-help.ts`). On a failed edit, a `tool_result` patch appends what pi's bare "could not find the exact text" leaves out: the nearest lines of the file (found by character-pair similarity to the first line of `oldText`), shown exactly so they can be copied, and whether only whitespace differs; for "found N occurrences", the line numbers of the matches and the `replaceAll` option. A file over 4 MB gets no hint.
- **replaceAll.** The extension registers pi's `edit` tool again under the same name (so every permission rule, the scope veto, plan mode and file history still apply) with an optional `replaceAll` on each edit, which changes every exact occurrence of its `oldText` (a CRLF file stays CRLF). The call's other edits go through pi's own tool first, then each replaceAll edit is applied to what is on disk; a replaceAll `oldText` that is missing fails the whole call before anything is written. Without `replaceAll` it is pi's tool unchanged (`test/pi-smoke.test.ts` checks the replacement mechanism on each pi bump).

Not done: pi's `read` has no PDF or notebook support and no per-line length cap (it truncates a whole result at 2000 lines or 50 KB); Claude Code's line-numbered read output was left out on purpose (it costs tokens, and the edit tool matches text, not line numbers).

## The scope veto (ticket 219)

`pi/extensions/toriel-veto.ts` is a pi `tool_call` handler that can only block (`{block, reason}`), loaded into every child like the other extensions (a missing file fails the resources audit, so the daemon will not start without it). For a directory-scoped session in deny mode it blocks, whatever the permission rules say: a `write`/`edit` whose target (`~` expanded, relative to the session cwd, symlinks followed through the nearest existing ancestor) is outside `TORIEL_SCOPE_ROOT` (scratch under `/tmp` is exempt unless the root is there), a `write`/`edit` with no usable path, every write when the scope is unusable, and a bash interpreter payload naming a path outside the root (the 218 check). Unlike the `toriel-grants` link's scope guard, which runs only when a rule says `ask`, it also sees calls a rule allows outright, so an allow rule or a project config can no longer open the boundary for these tools. Ask mode and sessions without a scope are untouched, it never prompts, and it cannot allow anything. The link keeps its own check as a second opinion. **The project's `.pi` directory (ticket 223).** In every scoped session, in ask mode too, it also blocks a `write`/`edit` whose target is inside `<root>/.pi` (`protectedEscape`: the directory itself, anything under it, reached through `..` or a symlink alike). That directory is pi's project configuration: the project layer of the permission policy (`.pi/extensions/pi-permission-system/config.json`, `.pi/agents`), packages and extensions, which pi layers over the user's policy in a trusted project and which outranks it. An agent that could write it could allow what the user's rules ask about, and the root is where it may write. No dialog is offered: the reason tells the agent to ask the user. For bash, the sandbox keeps an existing `<root>/.pi` read-only (`derivePolicy`, beside the `.git/hooks` carve-out). **Known gap:** a `.pi` that does not exist cannot be carved out (a missing path cannot be bound, and binding one would create it in the root), so a bash command can still create one; pi reads a project's config only once the project is trusted. This replaces the local patch to pi-permission-system (it withheld the project layer from every scoped session; removed, with its `permission-package-scope-patch` doctor finding). A patched copy still installed does no harm: it only keeps ignoring the project layer for scoped sessions until the next package update drops it. Not covered: bash commands other than interpreter payloads (the sandbox's job), MCP tools with path arguments, and the protected-file check (the grants file and the user's own pi config, outside the root), which stays an ask the user decides, since a veto would take that choice away. Why: `docs/permission-gate-decision.md`.

## Writes that leave the tree (tickets 217, 218)

Two lexical checks close the plain forms of "a command writes outside the working tree"; neither is a boundary (the sandbox is). **Auto mode's floor (217)** also asks about a bash command whose redirection target (`>`, `>>`, `2>`, `&>`), `tee` file, `cp`/`mv`/`install`/`ln` destination or output flag (`curl -o`, `wget -O`, `tar -C`, `sort -o`) is absolute, `~`, `$VAR` or `..` (`/dev/null`, `/tmp` and `.` are fine). **The scope guard (218)**, in deny mode only, denies a bash ask that hands code to an interpreter (`python3 -c`, `node -e`, `sh -c`, `perl -e`, ...) when that code names a path not provably inside the scope root (`~` and `$HOME` expand to the home directory, any other `$VAR` counts as outside, a `..` path resolves against the session's cwd, which is the root, and `/tmp`, `/var/tmp` and `/dev/null` are exempt unless the scope itself is under `/tmp`); the denial says to put the code in a script under the root. It sees only asks: a bash command your rules allow outright never reaches it, and a payload that builds the path at run time is the sandbox's job. `toriel doctor`'s `grants-path-rule` also flags an `external_directory(_write)` allow that covers the grants file, since a bash command writing it is that kind of ask, not a `path` ask.

## MCP servers (tickets 209, 216)

toriel owns the MCP config: every server is in `~/.config/toriel/mcp.yaml` (beside `settings.yaml`; `TORIEL_MCP` overrides), and pi's own `mcp.json` is not used. The file has one top-level key, `servers`, a mapping of server name to entry:

```yaml
servers:
  git:
    command: node            # run over stdio (or url: for a remote server)
    args: [/path/to/toriel-git-mcp]
    exposure: direct         # direct, codemode (default), deferred or hidden
    timeout: 300             # seconds
  freecad:
    url: http://127.0.0.1:39280/mcp
    whenUp: true             # only when something listens at the URL as a session starts
```

An entry holds `command` + `args` + `env` + `cwd`, or `url` + `headers` (exactly one of command and url), and `type`, `exposure`, `toolExposure`, `enabled`, `timeout`, `description` as pi's own entries do, plus toriel's `whenUp` and `readOnly` (the server's tools change nothing, so plan mode lets them run; ticket 229). An entry that cannot be used is left out of the session and named in a warning at session start (and by the doctor); the others still load.

- **How it reaches pi.** The `toriel-mcp` extension (loaded into every child that has MCP support, `profileHasMcp`) reads the file at session start and registers each server with `pi.registerMcpServer`; pi's built-in MCP extension then connects, declares and reports them like servers of its own `mcp.json`, so exposure, `/mcp` and sign-in work unchanged. A session started with `--no-mcp` or `--no-extensions` (worker profiles) is not handed the file. A change to the file applies to sessions started after it, or `/reload`.
- **`whenUp`** is for an app's bridge that exists only while the app runs (the FreeCAD bridge is the FreeCAD GUI). pi connects every server eagerly and warns about each that fails, which is noise in every session for one that is down on purpose. A `whenUp` server (URL servers only) is registered only when something accepts a TCP connection at its URL at that moment (800 ms), so a down one costs milliseconds and prints nothing. **`/mcp-up [name]`** looks again and says what it did, for the app started after the session was; it never unregisters.
- **`/mcp add` and `/mcp remove`** edit this file through its YAML document (comments and order are kept; written mode 0600), then reload the session. `/mcp status` and `/mcp explore` read it for the configuration they show. pi's own `/mcp` panel can still enable, disable or sign in, but its changes to a registered server last for that session only: change the file for a permanent one.
- **Bearer tokens and headers (ticket 10).** A URL server's `headers` map goes on every request; pi substitutes `${VAR}` from the environment and runs a value that starts with `!` (the command must make up the whole value). A server with an `Authorization` header is not offered OAuth sign-in. `/mcp add <name> <url> --token`, `--bearer-env VAR`, `--header NAME=VALUE` and `/mcp token <server>` write the header (see the `/mcp` command); `/mcp status` and the doctor show header names with their values hidden. A `${VAR}` is read from the daemon's environment, which is the shell that first started it: after exporting a new variable, `toriel kill-server`. The masked prompt is `secret-prompt.ts`; the controller's `askSecret` owns every key while it is open.
- **Moving from `mcp.json`.** `toriel doctor --fix` adds every server of pi's `~/.pi/agent/mcp.json` that is not in `mcp.yaml` yet, and sets the old file aside as `mcp.json.bak-<time>` (pi would otherwise start the old entries itself; a same-named disabled entry there would even mask the registration). Keys `mcp.yaml` does not know are listed rather than carried over. Mark an app's bridge `whenUp: true` by hand afterwards; the move does not guess which ones are.
- **Protected.** `mcp.yaml` is a protected path like pi's own config and the grants file: an ask about it always reaches the user, and auto mode never answers it, because an entry there is a command the next session runs.
- **What is not supported.** A project's `.pi/mcp.json` override (pi's own file is not read at all), `whenUp` for command servers (there is nothing to probe), and requests to pi: why toriel owns the file is in docs/design.md "MCP servers that are not always up".

## Doctor

`toriel doctor [--fix] [--yes]` in a shell and `/doctor [--fix]` in a session or the switcher print one report of everything toriel needs, graded: **required** (toriel does not work without it: node and the dependencies, the socket directory, pi's config directory, pi's `cli.js`, toriel's own extensions, skills and theme, no old toriel links), **recommended** (a valid toriel settings file, which exists: when there is none, `--fix` writes the commented defaults; pi-permission-system installed with a usable config), **optional features** (an old `settings.json` is converted to `settings.yaml`; pi's own `mcp.json` must hold no servers (they move to `mcp.yaml`, one `--fix`: the missing ones are added, the old file is set aside as a backup) and `mcp.yaml` must have no unusable entry (each is named with why); permission grants need `"toriel-grants"` in the package's `authorizerChain`; the shipped `code-review` and `git-archaeology` agents need an MCP server named `git` (toriel-git-mcp) with `exposure: direct` in toriel's `mcp.yaml`, because pi never declares a `codemode` server's tools to the model, so an agent limited to them would have none (the same goes for the `debug` and `crash-analysis` agents' `gdb` server and the `re-explain`, `re-find`, `re-trace` and `binary-diff` agents' `ghidra` server, one check each); every tier in the settings' `agentLanes` must name a provider pi knows (a key of `models.json`'s `providers` or a login in `auth.json`; a provider set up by an environment variable is not seen, so that check can be a false alarm); the shipped `research-web` and `advisory-diff` agents need `pi-web-access` in the `packages` of pi's `settings.json` (and a search provider set up for it) for its `web_search` and `fetch_content` tools; unless `"sandbox": "off"` is set (the sandbox is on by default), bubblewrap must really run (the doctor runs it once; `which` is not enough, unprivileged user namespaces can be disabled) or every scoped session's bash is refused; scheduled runs keep the machine awake only with `systemd-inhibit` on PATH; clipboard paste and `/btw`'s copy need `wl-clipboard` on Wayland or `xclip` on X11; the theme renders as intended only on a truecolor terminal, checked when `toriel doctor` runs in one; inside tmux, Shift+Enter inserts a newline only with `set -g extended-keys on`, and in kitty also only with `map shift+enter send_text all \x1b[13;2u` in kitty.conf (kitty does not negotiate extended keys with tmux and sends a plain Enter otherwise), both checked when `toriel doctor` runs in a terminal under tmux; Each problem says how to fix it and ends in `[fixable: <the edit>]` when `--fix` can do it, or `[manual: <why not>]` (a package install, a machine-specific value such as a missing MCP server's command, a security posture you chose, a config shape an edit could clobber); the closing line counts both. The command-line report exits 1 only when something required is wrong, so a script can gate on it; the `/doctor` panel leaves passing checks out and counts them (a short panel is easier to read, though it scrolls now). Both are coloured: green `ok`, red `PROBLEM` and problem count, dim `skipped`. The command line colours only on a terminal with `NO_COLOR` unset (`wantsColor`, plain ANSI), so `toriel doctor | grep` and logs stay clean; the panel uses the controller theme (`PANEL_STYLE`). The words, the exit code and `--fix` are unchanged.

`--fix` applies only the fixes that are safe to automate: edits to an existing, valid pi-permission-system `config.json` (add `"toriel-grants"` to `authorizerChain`; add the `path` rule for the grants file, an existing rule for that file moves last and becomes `ask`; everything else is untouched) and, for the MCP-server exposure checks, one edit to `mcp.yaml` (the original kept as a backup): set `exposure: direct` on a server entry that is already there but not exposed directly (an entry that is missing entirely needs the server's own command, so there is no automatic fix). It shows a line diff first, asks (`toriel doctor` needs `--yes` when nobody is at the terminal; `/doctor --fix` asks with a Cancel/Apply panel), copies the original to `<file>.bak-<time>` and rewrites the file as two-space JSON (comments, which JSON does not allow, cannot be preserved). It never installs a package, never writes a starter policy, and offers nothing for a config of an unusual shape. `toriel doctor` runs the start-up checks (node, dependencies, socket directory) first and stops there if they fail, so it explains a missing dependency instead of crashing on it.

**litellm model metadata (ticket 215).** `toriel doctor` (the command line asks the proxy itself and may wait a few seconds; the daemon asks once, a moment after it starts and off the event loop, and keeps the routes it was told in `litellm-routes.json` in the state directory (ticket 221), so the controller's notice line, the daemon log and the in-app `/doctor` show the same finding without a network call of their own, redoing the comparison against models.json as it is then, so a fix clears it; with no cache for the proxy models.json names, `/doctor` lists the check as skipped) asks the `litellm` provider of pi's `models.json` for `/model/info` (the credential is resolved the way pi does: a `!command` is run, an environment variable's name is read, else the text is the key, and it travels to the request in the environment, never on a command line) and compares `contextWindow`, `maxTokens` and `cost` of each model entry with what litellm states; a stale entry is a `litellm-models` finding with a fix that rewrites just those fields (the original kept as a backup). litellm reports its own configured metadata for a route, not the backend's real limits, so this copies litellm's belief; routes litellm serves that `models.json` lacks, and entries it no longer serves, are mentioned but never edited. An unreachable or unauthorised proxy is silent. **Bifrost gateways (ticket 221 follow-up).** Any provider of `models.json` whose key contains `litellm` or `bifrost` (`bifrost`, `work-bifrost`, ...) is a gateway and is checked on its own; no other provider is ever asked, so a credential only goes to a host toriel was told is a gateway. A bifrost provider is asked `GET <base>/v1/models` (the base URL with a trailing `/v1`, `/openai` or `/openai/v1` removed; the key as a bearer token, which a virtual key may be; the list is followed through `next_page_token`), and each model id (`provider/model`) is compared on `context_length` (else `max_input_tokens`) with `contextWindow` and `max_output_tokens` with `maxTokens`; cost is not compared for bifrost, because its per-token prices state no unit in the API reference. The finding is `bifrost-models`, and its fix rewrites only that provider. This follows bifrost's documented API and has been tried only against a stand-in server, not a live gateway: if it finds nothing where you expect something, the reply shape is the first suspect.

At start-up the daemon logs every finding (`WARNING [level]: ...`) and the controller's notice line shows the required and recommended ones in full plus "N suggestions: /doctor lists them" for the rest, refreshed every 10 s. `warnNoPermissionSystem: false` silences the permission-related items there (the explicit report still shows them). The checks live in `src/doctor.ts` (`CATALOG` is the list; `collectFindings` makes them) and `src/resources.ts` (`auditFindings`); adding a requirement means adding a check (AGENTS.md).

## Permission grants

A permission prompt (pi-permission-system) can be answered "allow for 1 hour" or "allow for this session, kept across restarts", and `/permissions` lists, adds and revokes such grants. pi itself only remembers its own "for this session" answer in memory (lost on `/reload`, respawn and daemon restart, and it cannot be listed), so toriel keeps the grants: the daemon (`permissions.ts`, file `permissions.json`, mode 0600, `TORIEL_PERMISSIONS` overrides) holds them per session UUID, with an optional expiry, at most `permissionGrantLimit` per session. Design, threat model and spike results: `docs/permissions.md`.

- **Enforcement.** The `toriel-grants` extension registers an authorizer link in pi-permission-system. When a request lands on `ask`, pi runs the links named in `authorizerChain` (in the package's `config.json`) before the dialog; the link sends the daemon `permission_check {uuid, grants, value}` (`grants` is pi's suggested session grant for the ask) and allows when every suggested pair has a live, active grant with the same surface and exactly the same pattern, else defers to the dialog. Every failure (daemon down, no answer within 1 s, an error) defers: more prompting, never less. A link that threw would block the tool call, so nothing in it can throw. Since ticket 163 the link also carries the scope guard: when the daemon set `TORIEL_SCOPE_ROOT` in the child's environment, covered write asks (`external_directory_write`, `external_directory`, `path_write`) whose canonical target is outside that directory are denied with a reason naming the path and the scope root in deny mode, or deferred to the dialog in ask mode - since ticket 172 every agent-profile session is scoped to its launch dir (deny exactly at a linked-worktree root, ask elsewhere) - before the grants check; the deny-mode half fails closed (an invalid env denies every covered write rather than defering) while ask mode fails to prompting (an invalid env defers every covered write). See "Env" for the full contract and its limits. You must add `"authorizerChain": ["toriel-grants"]` to that config once; toriel never edits it (the resources audit prints the line).
- **The prompt.** A permission prompt (a `select` titled "Permission Required" with a plain `Yes` and `No`) is always drawn in toriel's own layout, whether or not the daemon has a suggestion (`withOwnLayout` in `src/dialogs.ts`): `Yes, this once` / `Yes, and allow "<pattern>" for 1 hour` / `... for this session, kept across restarts` / `No` / `No, with a reason`. Each row maps to one of pi's literal answers (`answers`; `answerValue` is applied where the answer is sent), and an allow row answers `Yes` and sends `permission_add` (source `dialog`). When the link finds an ask uncovered, the daemon keeps pi's suggestion for the session and attaches it to the next `select` dialog whose title names the same command (whitespace ignored; asks are serialized per session) as `request.toriel = {grants}`; one allow row per `permissionGrantDurations` entry follows. pi's own "for this session" row is never shown (pi keeps it in memory, out of toriel's sight and limits); with no grant to offer it stands in for the session row, labelled as pi's. A prompt about the grants file or pi's config is marked `toriel = {protectedAsk: true}` by the daemon (from the title, suggestion or not) and gets once / No / reason plus a dim note, no allow row at all. Tab on an allow row (single-grant asks only) edits the pattern inline before the grant is stored, with a cursor (left, right, home, end, delete, backspace; `DialogPanel`; `inlineReason` in `src/session-actions.ts`). The 700 ms arrival guard, esc = No, and the reason flow are as before. File-path asks work the same (ticket 194): a file-path grant is stored first, with `permission_add`'s `dialog` naming the open prompt (the daemon refuses it without that, and refuses a pattern that does not cover pi's suggestion), and pi is answered `Yes` only after that. Since ticket 246 the daemon's whole-tree protection of `~/.pi/agent` carves out the two agent-maintained memory subtrees (`pi-hermes-memory/skills` and `projects-memory`) on file-path asks, so a grant can cover a Hermes skill or a project memory write; the collapsed reading is checked too, so a `..` run out of a carved tree fails closed, and everything else under pi's own directory stays protected. Other selects (an extension's own picker) are left as pi sent them. A subagent's prompt is answered from its parent's view only by the controller attached to the parent. Notices about what the daemon did (`notice` with `durable: true`: a grant answered a prompt or expired; `exited`) become a dim "toriel: ..." row in that session's transcript (`noteRow`, `SessionView.notes`), not a four-second flash.
- **`/permissions`** (in a session: this session's grants; in the switcher: every session's) `[list | add <surface> <pattern> [--for 1h|--session] [--note ...] | revoke [id|pattern] [--all] | restore]`. `revoke` with no argument opens a pick list. Surfaces: `bash`, `mcp`, `tool`, `skill`; the pattern is matched exactly (as pi's prompt offers it, e.g. `bash "git status"`), not as a wildcard. The status line shows `permissions N, next ends HH:MM`; timed grants simply stop matching when they expire (a notice says so within 30 s).
- **File-path grants.** pi downgrades a link's `allow` on file-path surfaces (`path`, `external_directory` and their read/write forms), so the link never answers those. The daemon does instead: a later file-path prompt whose every suggested pattern is covered by a grant made from an earlier prompt is answered `Yes` by the daemon before any controller sees it (`answerCovered` in `src/daemon-children.ts`, `answerablePrompt` in `src/daemon-permissions.ts`; a notice names the grant). `/permissions add` still refuses these surfaces; only a prompt answer makes one, and the grants file and pi's own config directory are never answered from a grant. Details and guards: `docs/permissions.md` "Limits that follow from the chain".
- **Deny-after (ticket 88).** Opt-in, never the default: a permission prompt that waits for ever stays the rule (docs/permission-dialogs.md req 5). `/deny-after <duration|off|default|status>` (`deny_after`, protocol 11; `handleDenyAfter`) sets how long one session's prompts may wait, and the `permissionDenyAfter` setting (a duration from 10 seconds to 24 hours) sets it for every session; the command wins (`off` waits for ever whatever the setting says, `default` follows the setting again), and it is kept in the daemon's memory only. When a permission prompt has been open that long with no answer, the daemon answers pi "No" exactly as a user's No would (`ChildManager.armDeny`), clears the open dialog and badge, and writes a durable notice under the tool call, `denied automatically: nobody answered in 10m: <command>`, so the transcript shows it was automatic. A question an agent put to the user (the ask-the-user tool, another extension's picker; ticket 227) waits the same time and is then dismissed as if the user had cancelled it, with the notice `dismissed automatically: nobody answered in 10m: <question>`. Only a select titled `Permission Required` with Yes and No is a permission prompt (`isPermissionPrompt`), so auto mode and grants never answer a question that happens to offer Yes and No. The timer starts when the prompt arrives and ends with any answer (a controller's, a grant's, auto mode's). Auto mode answers first, so a session with both only waits on the prompts auto mode leaves to the user. `TORIEL_DENY_MIN_MS` lowers the 10-second minimum for tests.
- **Auto mode (ticket 213).** `/auto [on|off|status|<duration>]` or `shift+tab` (the toggle; `auto_mode`, protocol 10; `SessionCommands.auto`, `handleAutoMode` in `daemon-handlers-ops.ts`) makes the daemon answer a session's permission prompts "Yes" itself, so a long stretch of agent work does not stop at every probe and build step. It sits in the same place as the file-path answer above, `ChildManager.answerAuto` in `daemon-children.ts`, which sees every dialog before a controller does and runs AFTER `answerCovered`, so a grant you made wins first and auto mode fills in what grants do not cover. Every answer is a durable notice (`allowed by auto mode: <command>`) that reads under the tool call it allowed (the same attach as the grant notice). The always-ask floor (`floorReason` in `src/auto-mode.ts`) still reaches you, with a flash saying why (`auto mode still asks about this one: ...`): the grants file and pi's own configuration (the `touchesProtected` check, with ticket 246's memory-store carve-out on non-bash asks only, since a command's `..` run cannot be resolved across squashed `&&` tokens), credential and secret files (`.ssh`, `.aws`, `.env`, `auth.json`, `models.json`, `*.pem`, ...), writes outside the session's directory (the `external_directory_write` surface; reads outside are allowed), destructive commands (`rm` and friends aimed outside the tree or at all of it, `dd of=`, `mkfs`, `wipefs`, recursive `chmod`/`chown` outside the tree, `find -delete`), pushes and publishes (`git push`, `gh pr merge`/`release`/`repo delete`, `npm`/`cargo`/`gem`/`twine`/`docker` publish or push), privilege escalation (`sudo`, `doas`, `su`) and code piped from the network (`curl ... | sh`). Anything pi itself denies never becomes a prompt, so a `deny` rule of yours (`sudo *`) stays denied. **An `ask` rule you wrote stays asked** (ticket 213 follow-up): the grants link reads why pi asks from the package's own policy (`askRule` in `toriel-grants.ts`, through the `PermissionQuery` pi hands a link; sent with `permission_check` as `rule`) and auto mode answers only asks that come from the catch-all default (a bare `*` rule, the built-in fallback); a rule with a specific pattern in any of your config scopes, a package safety floor and a fail-closed scope all stay asked, with a flash naming the rule. When the link cannot tell (an older link, a surface it reads differently) auto mode asks too: unknown is never a yes. So with `*: ask` as your default auto mode fills that in, and every more specific ask you wrote still reaches you. **The floor is a lexical check on the command's text, so it is a convenience and not a boundary**: a command can hide what it does (`eval`, a variable, a script written a moment ago; `sh -c '...'`, `python -c` and the like are asked about outright for that reason, and `sudo` is recognised by its path too); a directory-scoped session with the sandbox on is the real boundary. The mode lives in the daemon's memory only (never stored, so a daemon restart ends it, unlike grants), is per session (a subagent does not inherit it), and `/auto 2h` makes it end by itself (at most 24h; a notice says when it does). The status line shows `AUTO MODE` (with the end time when there is one) right after the session's name and never drops it on a narrow terminal. It answers only prompts that look like pi-permission-system's (`select` with `Yes` and `No`), never another extension's select.
- **Limits.** Grants made through pi's own "for this session" answer are invisible to toriel. Deleting a session removes its grants; stopping or parking keeps them. An in-process pi subagent shares its parent's `TORIEL_SESSION_ID` and so matches the parent's grants.
- **Tamper resistance.** The file is a stored "yes", and an agent runs as you. Grants read from disk at daemon start are DORMANT: they do nothing until `/permissions restore` in that session (the status line says "N saved grants off (/permissions restore)"). The confirmation is in memory, once per daemon start per session, never stored. Grants made in the running daemon apply at once. The daemon also refuses `permission_add`, `permission_revoke` and `permission_restore` from a connection that has not announced itself as a controller (first line `list`), which stops accidental self-grants only: a caller that sends `list` first gets through, as anything with the socket can. The resources audit also warns when no `path` rule (`ask` or `deny`) covers the grants file and prints the line to add (an `ask` lets an agent write it with your approval). That rule is a speed bump, not a wall: it stops the write tool, redirects, `sed -i`, `cp` and `cat`, but a shell that builds the path indirectly (`python -c`, variables) gets past it.

## Side questions, performance reviews and mouse clicks

`/btw` (`btw.ts`) copies the session file to a temp dir and runs `pi --print --session <copy> --no-tools --no-extensions --no-skills --no-prompt-templates --no-context-files [--model m] <prompt>`; the prompt (`btwPrompt`) says there are no tools and nobody to answer follow-ups. The copy is deleted afterwards, so the session file is never touched and a sleeping session stays asleep. The answer goes to the `InfoPanel` (which wraps long lines under their own indent, `wrapHanging`) with actions (`PanelAction`: `c` copies via `Host.copyText`, `s` writes `btw-<time>.md` under `$XDG_DATA_HOME/toriel/btw/`). Not verified against a real model with tool-call history and `--no-tools` (some providers may reject tool calls without tool definitions; the error is shown).

`/performance` (`performance.ts`) is the same machinery with a built prompt (`performancePrompt`): the session file is copied to a temp dir and the copy (not the original) is what `pi --print --no-tools ...` reads. `runPerformance` reads the file once, profiles the whole transcript with `profileTranscript` in `performance-profiler.ts` and caps the copy with `capTranscript`; both the prompt and `truncated` come from that single pass. The prompt is the review prompt plus a framing line plus `renderProfilerStats(stats)` - a compact block of mechanical stats (session span and entry count, per-model requests/tokens/cost and the session-wide cacheRead vs input+cacheWrite ratio, per-tool calls/errors/total duration/output bytes, the five biggest single tool outputs, file paths read more than once, exact shell-command repeats plus a normalized repeat count when collapsing digit runs and quoted strings finds more, the three longest tool durations, the three biggest gaps between consecutive assistant messages, and compaction count with the last `tokensBefore`), every list capped at five. The profiler is a pure one-pass text scan (`profileTranscript` takes the transcript string; no fs) that skips malformed lines exactly like pi's `parseSessionEntries` does, so the model interprets measured numbers instead of the raw text; `durationMs` is optional on pi's entries, so durations are summed where present and the renderer says `n/a` when nothing has one. The copy pi reads keeps the session header (first line) plus the most recent whole lines within `TRANSCRIPT_TAIL_BYTES` (256 KiB), with an omission note line between them; a line over `TRANSCRIPT_CLIP_LINE_BYTES` (64 KiB, one huge tool output) first has every string value over `TRANSCRIPT_CLIP_CHARS` (8000) characters cut to a `...[N characters cut]` marker, so the entry survives as valid JSON instead of being lost or breaking the line. pi skips the note line and any malformed line, so the copy pi loads is the header plus the kept tail chain and nothing else; over the cap the prompt says the earliest entries were dropped and to judge only what is there. The side run goes through `sideRun` in `btw.ts` (which takes an optional `prepare` transform the copy passes through; `askBtw` is unchanged behaviourally). The timeout is `PERFORMANCE_TIMEOUT_MS` (5 minutes), SIGKILL as in /btw. Because the run has no tools it cannot read anything at all (pi's `auth.json` and `models.json` included). The handler reads the session file and spawns pi itself, so it does not call `liveMeta()` and a sleeping session stays asleep. On completion the report is auto-saved to `$XDG_DATA_HOME/toriel/performance/` as `performance-<time>.md` (`savePerformance`) and delivered into a top-level review session: `SessionCommands.performance` calls the host's `openReviewSession` (a seam added to `Host`; session-command handlers cannot talk to the daemon directly, so the controller implements it) BEFORE the analysis runs - the view enters the review session at command time, so the switch never happens mid-work later. The controller seeds a session file with pi's `SessionManager.create(cwd)` plus one user message (`performanceReviewSeed`: the analysis is running and the report will arrive here as a message; treat it as this session's starting context) and spawns on that file (`{ type: "spawn", sessionFile, name, ready: true }`, the same resume path as `startViewed`), entering the view immediately (switch now if the child's meta is loaded, otherwise `pendingEnterId`). When the analysis completes, the report goes to the review session as a `{ type: "message", to: <child uuid>, text }` delivery - the same path other sessions use, so the session's bridge injects it and the session starts its turn on the report. A delivery failure (or no review session at all) only costs the delivery: the auto-saved file still holds the report and the notice says so. The name is `performance review <YYYY-MM-DD HH:MM>` (`performanceReviewName`, zero-padded, local time), uniquified like any session name.

pi-tui turns a press and release on one cell into a `click` that pi's thinking blocks and tool output toggle on. `click-guard.ts` wraps the screen's private `dispatchMouseToLayout` so only `clickCount >= 2` clicks reach the transcript (`TORIEL_CLICK=single` disables the guard). Presses, drags, the wheel and text selection are untouched.

## Dialogs that go stale

A permission dialog is held by the daemon (`pendingDialog`, `lastDialog`) until answered. It is also dropped when the turn settles (`agent_settled`) and when the dialog's `timeout` passes (pi resolves such a dialog itself and says nothing). The controller drops its open dialog when the session list says none is pending, asks the daemon again (`attach`, which resends the waiting dialog) when the list says one is pending for us and none is open, shows and answers a dialog only while its session is on screen (with the switcher up the dialog stays pending, the row says "waiting on permission", and entering the session shows it again), and keeps an open dialog when the history reply replaces the view (the daemon sends the dialog just before the history).

## Waking sleeping sessions

A session that was stopped, or not started since toriel restarted, has no pi process. Commands that need one (`/model`, `/compact`, `/clear`, `/mcp list`, `/mcp explore`, `/reload`, `!command`) start it themselves through `SessionCommands.liveMeta()`; no message is needed. Commands that do not (`/in` and the other schedule commands, `/name`, `/park`, `/publish`, `/comment`, `/btw`, `/performance`, `/fork`, `/parent`, `/detach`, `/why`, `/feedback`, `/abort`, `/background`, `/auto`) leave it asleep, and ones that send a prompt (`/init`, `/mcp reconnect`) wake it through the ordinary prompt path. The wake is per command, not a framework flag, because most commands should not start a process; the rule for new commands is in AGENTS.md.

**Typing wakes it too (ticket 68).** Completions that ask the child (pi's own command list, `/mcp explore <TAB>`, `/model` names) need a running process before the command is sent, so when the editor text starts with `/` or `!` and the typing pauses for 400 ms (`wake-on-type.ts`; `/` typed and deleted starts nothing), the controller asks the daemon to start the viewed session (`spawn` with `wake: true`), shows `starting session...`, and re-fetches pi's command list when it is up. Plain prose never triggers it, neither does opening a session to read it, and neither do toriel's own commands that never touch pi (`/help`, `/exit`, `/park`, `/name`, the schedule commands and the rest of the list above; `NO_CHILD_COMMANDS`, checked against the command table by a test). It does not fire for a session that is already up, is view-only (attached in another controller), is open in another pi (`externallyLive`), is a subagent (its parent owns the lifecycle) or while the session list is open; the daemon also refuses (`woke: false` with a reason, shown as `session not started: ...`) a file it never ran that was written in the last minute, the same signal as the confirm-fork prompt, and a file another pi has open. Parked sessions do wake: typing into one is the use that unparks it. The start is one shared one: `startOnce` makes the in-flight start `s.starting`, and a prompt, a second wake or `/new` arriving meanwhile awaits it instead of failing with `spawn in progress; retry` or starting a second process. Nothing puts an idle session back to sleep (ticket 68 assumed an idle-sleep timer; there is none), so a session woken and then abandoned stays running until `/stop` (ctrl-k), `/park` or a daemon restart; the `/`-or-`!` condition and the debounce are what keep that rare. The `/` or `!` state of the editor is what counts: the debounce looks again when it fires, so a session switch or a cleared editor in between cancels it.

## Session ids and names

A session's address is its UUID (pi's session id). toriel picks it before pi starts (`--session-id`) for new sessions and reads it from the file for resumed ones, and tells the child as `TORIEL_SESSION_ID` in its environment (not set in the pi child of a fork, whose id pi chooses after it starts and an environment cannot change after spawn; there the agent's bash still has `PI_SESSION_ID`, and a `!command` gets both, since the daemon learns the id and builds that environment per command). The daemon command `resolve` turns a UUID, UUID prefix, `#number` or name into a session, falling back to the files on disk when the daemon does not hold it. Names are made unique when you set them (`/rename`, `/new -n`, `/fork`): a taken name gets ` #2`, ` #3`; names that pi or another program wrote can still collide, and `resolve` then reports the match as ambiguous.

## Env

- `TORIEL_SOCK` - socket path (default `$XDG_RUNTIME_DIR/toriel.sock`). The daemon
  also puts it in every child's environment as `TORIEL_SOCK`, which is how the
  extensions find it. The pidfile/lock is `daemon.pid` in the data dir, not next to the socket.
- `TORIEL_PROFILE` - name of an isolated instance (also `toriel --isolated [name]`): everything below moves under `$XDG_RUNTIME_DIR/toriel-<name>/`, see "Developing toriel"
- `TORIEL_FILE_HISTORY_DIR` - where the write/edit tools journal what they change, per session (default `file-history` in the state directory; ticket 11). The daemon gives each child it starts the path as `TORIEL_FILE_HISTORY`.
- `TORIEL_MCP` - the MCP config file (default `mcp.yaml` beside the settings file; tests point it elsewhere). The daemon gives each child that has MCP support its path as `TORIEL_MCP_FILE` (a path, never the contents: an entry's `env` may hold a secret, and a child's environment is readable by the agent's own commands).
- `TORIEL_PI_CLI` - pi cli.js the daemon spawns as children (tests point this at the fake pi)
- `TORIEL_LOG` - daemon log (default `~/.local/state/toriel/daemon.log`, `$XDG_STATE_HOME` honored; kept under 5 MB: over that it moves to `daemon.log.1`, checked at start and every 10 minutes)
- `TORIEL_TRASH` - trash dir (default `$XDG_DATA_HOME/toriel/trash`; it may be on another filesystem than the session files, as in an isolated instance on tmpfs: moves in and out fall back to copy and delete)
- `TORIEL_PROVIDER` / `TORIEL_MODEL` / `TORIEL_THINKING` / `TORIEL_STEERING_MODE` -
  override the settings file: provider, model and
  thinking level for spawned
  children (e.g. `TORIEL_PROVIDER=litellm TORIEL_MODEL=local-model` for free
  local tests, or `TORIEL_MODEL=glm-4.7 TORIEL_THINKING=low` for cheap test
  fleets); unset = your normal pi settings
- `TORIEL_SETTINGS` - path of the toriel settings file, instead of `settings.yaml` in the config directory (see Settings)
- `TORIEL_SUMMARY_MODEL` - model for /summarize and /why (overrides `summaryModel`)
- `TORIEL_AUTO_NAME=0` - never name sessions automatically (the `autoName` setting does the same from the file; tests set it)

- `TORIEL_KEYS` - set to anything to log key and UI events to `logs/key-debug.log` in the repo (a value containing `/` is used as the file path)
- `TORIEL_CHILD`, `TORIEL_SESSION_ID`, `TORIEL_SOCK` - set by the daemon in every child's environment (the extensions read them; do not set them yourself)
- `TORIEL_SCOPE_ROOT` - set by the daemon (with `TORIEL_SCOPE_MODE`) in a child's environment when the session is scoped: any agent-profile session, scoped to the canonical realpath of its launch directory (the daemon computes it per launch, `src/scope-root.ts`; a `!command` never sees it). A profile with `scope: none` in its frontmatter is never scoped (the daemon does not set the variable for it). The scope link in `toriel-grants.ts` reads it once at registration and, per the mode, denies or defers `external_directory_write`, `external_directory` and `path_write` asks whose canonical target is outside that directory (bash writes reach it through the same surfaces; reads are not jailed in this phase). Failure contract: absent = the guard is off and the link defers everything (the only opt-out; the daemon simply does not set it); present but not an existing canonical absolute directory = in deny mode every covered write is DENIED with a reason naming the env failure, never deferred or silently disabled; in ask mode every covered write DEFERS to the dialog (the guard cannot know inside from outside, so it prompts - never silently allows, never denies). Limits: a session started in a subdirectory is scoped to that subdirectory, not to the enclosing worktree; a pi-permission-system config ALLOW on `external_directory_write`, the bare `external_directory`, or the `"*"` fallback (when no `external_directory_write` catch-all ask/deny answers) short-circuits the authorizer chain before the link and disables the guard - allows on `path`/`path_write`/`write`/`edit` gate in-cwd asks and do not reach it (the doctor's `scope-guard-short-circuit` check flags exactly those, but cannot prove every write is guarded - it only sees the config, not what a session does); if the link never registers (pi-permission-system older than the authorizer seam) there is no guard. Do not set it yourself; the daemon owns it.
- `TORIEL_SCOPE_MODE` - set by the daemon next to `TORIEL_SCOPE_ROOT` (never without it): `"deny"` or `"ask"`. Deny - exactly when the launch dir is the root of a linked git worktree (T1's contract): an outside-root covered write is denied with a reason naming the path and the root, before the grants check, and the guard fails closed. Ask - every other launch dir: the guard defers outside-root and unresolvable covered writes to the dialog/grants path instead of denying (more prompting, never less; never a silent allow). Honest limit (review finding F1): the link, in either mode, runs only on asks - a config ALLOW on the covered surfaces short-circuits BOTH modes before the link (the doctor's `scope-guard-short-circuit` check exists to flag exactly that for the global config). Ask mode's enforcement value today is as a boundary marker: it makes the outside-root verdicts explicit (a covered write the config resolves to ask is deferred by the link and answered by grants/dialog/parent; a headless child without a serving parent denies fast), and it is the seam a future pi-permission-system that can force prompts pre-config will flip on - the daemon side is done. Absent (an older daemon, a hand-set env) reads as deny, so an existing scoped session behaves exactly as T1 shipped. Do not set it yourself; the daemon owns it.
- `TORIEL_SANDBOX`, `TORIEL_SANDBOX_RW` - set by the daemon in a child's environment, never without `TORIEL_SCOPE_ROOT`, when the `sandbox` setting is `"bwrap"` and the session is scoped: `TORIEL_SANDBOX=bwrap` switches `toriel-jobs.ts` to the per-command sandbox (see "Command sandbox"), `TORIEL_SANDBOX_RW` is the `sandboxWritable` roots joined with `:` (`~/` expanded). Absent = no sandbox; present but not exactly `bwrap`, or without a usable scope root, = every command is refused (fail closed). The daemon drops both from the environment it inherits and from `!command`s and the `/btw` and summary side children. Do not set them yourself.
- `TORIEL_SHARED_DIR` - set by the daemon in every child's environment: the directory every sandboxed command may write (default `~/.local/share/toriel/shared`, under `$XDG_DATA_HOME`, mode 0700, created at daemon start; `TORIEL_SHARED` moves it for the daemon). Safe to point agents at it even when the sandbox is off. Treat what an agent reads from it as untrusted input.
- `PI_CODING_AGENT_DIR` - pass to BOTH processes in tests to isolate
  sessions/settings/extensions from your real agent dir

Pasting and selecting (Linux; `wl-clipboard` on Wayland, `xclip` on X11):
- `ctrl-v` pastes the clipboard: its text, or - when it holds only an image - an
  `[image #1 png 340 KB]` marker in the chat box; the picture is sent with the
  message (delete the marker to drop it). Refused with a message when the model
  takes no images, or the image is over 8 MB. In the transcript a message's
  images show as a PNG thumbnail (at most 40 x 12 cells, aspect kept) on a
  terminal that draws images (kitty, iTerm2; pi-tui decides, and turns it off
  under tmux/screen), and as a dim `[image]` / `[2 images]` line everywhere
  else and for non-PNG types. Live echo, live events and file replays all use
  the one `UserMessage` component. The base64 stays in memory with the row.
- Middle click pastes the primary selection (whatever you last highlighted).
- Text selected inside toriel is copied to both the clipboard and the primary
  selection, so either paste finds it. Shift+click still hands the mouse to the
  terminal.
- **Links**: a plain click on a URL in the transcript opens it in the browser (`xdg-open`; `open` on macOS). pi's markdown links URLs in assistant and user text; `linkify.ts` links them in tool output. Only `http(s)` opens (the link text is model output), and a failure shows a notice. A URL that wraps across lines is not linked in tool output (half a URL would open the wrong page); with `/mouse off` the terminal's own link click (kitty: ctrl+shift+click) works on the same links. Needs a terminal that supports OSC 8 (pi turns hyperlinks off under screen and tmux without forwarding).
- `/mouse [on|off|toggle]` (session view and switcher; no argument shows the state; `/mouse --help` describes it): `off` stops toriel's mouse reporting, so the terminal does select, copy and middle-click paste itself - also over SSH, where toriel cannot read your clipboard. While off, toriel's clicks (switcher rows, double-click on blocks) and its own selection highlight stop, wheel scrolling may stop depending on the terminal, and the terminal selects raw screen cells; the status line shows `mouse off` in a session. Not remembered across restarts. Shift held during one click does the same for that click only.
- **Over SSH or without a display** there is no clipboard tool to run (`WAYLAND_DISPLAY` and `DISPLAY` are unset on the remote), so selected text is copied through the terminal with OSC 52 escapes (`osc52.ts`), one for the clipboard (ctrl-v) and one for the primary selection (middle click). The terminal never says whether it accepted it, so the flash reads "Sent to the terminal clipboard (not confirmed)" rather than "Copied!". Your terminal must allow it: kitty and most others allow OSC 52 *writes* by default (kitty's `clipboard_control`, `write-clipboard write-primary`); *reads* (what ctrl-v over SSH would need) are off by default and toriel does not do them yet.
- **Inside tmux** the escape needs one of these in `~/.tmux.conf` (restart tmux or `tmux source-file`): `set -g set-clipboard on` (tmux handles the escape itself) or `set -g allow-passthrough on` (tmux 3.3+; tmux forwards it). toriel sends both forms under `$TMUX`, so either setting works; with neither the copy is dropped silently, which is why the flash says "not confirmed" and names both.
- **Paste over SSH:** ctrl-v and middle-click would read the *remote* machine's clipboard, which does not exist there, so toriel says so in the notice line ("over ssh there is no local clipboard to read...") instead of failing quietly. Use your terminal's own paste key: ctrl-shift-v for the clipboard, shift-middle-click for the primary selection (toriel has the mouse; shift hands it to the terminal). Both arrive as an ordinary bracketed paste.
- Copies were once slow to reach the primary selection (about 4s per target): `wl-copy` and `xclip` leave a background process that serves the selection and inherits their output pipes, so waiting for the pipes (`execFile`) took the whole tool timeout. Writes now finish when the tool exits (`runWrite` in `clipboard.ts`).
- Not covered here (data not yet written up): primary-selection quirks per terminal. The open ticket for reading the local clipboard over SSH via the OSC 52 query is separate.

The controller feeds it `ScrollView`'s `scrollTop`, `viewportHeight` and `isFollowingEnd`, and `onShift` scrolls the view by how far items above it turned out taller or shorter than estimated once drawn, so scrolling up does not move what you are reading; the `translateBox` in pi-tui's scroll layout applies that correction to the same frame it arrives in. Costs: the scrollbar is proportional to estimates until items have been seen, and a toggle leaves off-screen heights stale until they are scrolled to. `node probes/transcript-render.ts [session.jsonl] [--items N]` times the plain container against this one for a synthetic or a real session (8,007 real items: first frame 1.75 s -> 3 ms, tools expanded 2.4 s -> 7 ms).
- `editor.ts` - chat box (key interception, history bindings), `autocomplete.ts` (/command, @file and path completion; Tab inside a command that has its own argument completer, such as `/new -m` or `/model`, runs that completer instead of file completion, because pi-tui otherwise sends an explicit Tab after a space to files, ticket 247), `history-search.ts` (ctrl-r), `switcher.ts` - the list UI, `session-filter.ts` (the filter's matching)
- `info-panel.ts`, `choice-panel.ts` - the docked text (scrollable) and pick-one panels; `fence-info.ts` - which code-fence info strings stay visible; `binary-view.ts` - hexdump for binary files read by a session; `error-format.ts` - provider errors made readable
- `pi-settings.ts` - the few pi settings.json options toriel honors (wheel speed, hide thinking)
- `lifecycle.ts` - find/start/stop the daemon, `pi-theme.ts` - pi theme init

Shared: `shared.ts` (wire protocol, LF framing), `groups.ts` (session-groups.json),
`theme.ts` (all colors, read from `../pi/themes/solarized-dark.json`).

Repo root: `pi/` holds the pi-side resources toriel owns (extensions, the messaging skill,
the theme). `resources.ts` lists them and builds the `-e` / `--skill` arguments the daemon
adds to every child (explicit paths still load under `--no-extensions` / `--no-skills`, so a
profile with discovery off keeps toriel's plumbing; a minimal profile gets no skill).
Nothing is installed into pi's own config dir (`pi-dir.ts`: `$PI_CODING_AGENT_DIR`, default
`~/.pi/agent`), which holds the user's settings, models, MCP config and packages.
`toriel-presence.ts` is not loaded by toriel (it is for pi processes toriel did not start);
list its path under `extensions` in pi's `settings.json` to use it.
`theme-preview.ts` prints sample components in the active theme.

## Command syntax

toriel's own /commands (the switcher box and in-session) parse like a Linux CLI,
using [commander](https://github.com/tj/commander.js): `/fork --name "my fork"
focus on file B`. Every command has `-h` / `--help` (shown in a dismissable
panel). Multi-word values are quoted (`"two words"`, `'two words'`) or have
their spaces escaped (`two\ words`); put `--` before text that starts with a
dash (`/fork -- "-10 is the temperature today"`). Chat-friendly leniencies: a
quote only opens a group at the start of a word (so `You're` is fine), and a
backslash before an ordinary character stays as typed. Lines starting with `/`
whose name is not toriel's go to pi untouched.

Adding a command: add an entry to `SESSION_COMMANDS` or `SWITCHER_COMMANDS` in
`commands.ts` (name, description, and a `build` that declares options and
arguments on the commander `Command`), then add its handler to the handler
table in `session-commands.ts` / `switcher-actions.ts` - the compiler rejects a
table with a missing entry. Parsing, help text, error messages and the
autocomplete hint all come from the declaration. A command whose argument has a
fixed set of choices (`/model`, `/group`, `/mcp`) can also give a `complete` function
(see `CommandSpec` in `cli.ts`): typing the command and a space then pops up the
choices, narrowed by what is typed. Flags are not completed.

## Summaries

`/summarize` (switcher) writes a one-line summary of the highlighted session
into the Summary column, using a model run through pi's print mode:
`-m provider/id` (default: `summaryModel` in `~/.config/toriel/settings.yaml`,
else `litellm/local-model`), `-c <chars>` (transcript size, default 2500), `--all`
(every session with no summary or a stale one). Summaries live in
`session-groups.json`. They are kept up automatically: every
`summaryIntervalMinutes` (default 60, `0` turns it off) while toriel is open, it
summarizes sessions that have no summary yet or have gained at least
`summaryMinNewMessages` (default 6) messages since theirs, skipping any that
are running or were written to in the last 3 minutes. Most recently touched
sessions go first, at most 10 per pass, so a backlog of old sessions fills in
over several passes. Failures are logged and retried next pass.

## Feedback

`/feedback [-c category] <text>` (in a session or the switcher) records a note
about a harness or extension problem; `/feedback -l` lists the recent ones. Notes
go to `$XDG_DATA_HOME/toriel/feedback.jsonl` (`TORIEL_FEEDBACK` overrides), one JSON
object per line, so they can be investigated later by a person or an agent. Each
carries `source` (`user`, or `agent` for a future agent-facing tool), the session
file, pi's session uuid, model and provider, and the newest entry at that moment:
`session.entryLine` is its 1-based line in `session.file` and `session.entryId`
its `id`, so `sed -n '<entryLine>p' <file>` shows the turn. `at` (UTC) lines up
with `env.daemonLog`, and `env` has the toriel revision and pi version.

**The bundle (ticket 239).** Those fields only point at things on this machine, so every note also gets a folder, `$XDG_DATA_HOME/toriel/feedback/<time>-<id>/` (`TORIEL_FEEDBACK_DIR` overrides; the note's `bundle` field names it, and `/feedback -l` shows it), readable only by you (mode 0700/0600: a session holds everything the model saw). `src/feedback-bundle.ts` writes it, `runFeedback` in `src/feedback-command.ts` gathers its inputs, and nothing leaves the machine:
- `record.json`, the note.
- `snapshot.json`: what the daemon holds for the session at that moment (`feedback_snapshot`, protocol 13, `src/daemon-feedback.ts`): auto mode (and when it ends), plan mode, deny-after, whether a controller is attached, the agent profile (null = a plain session), the write scope (root and deny/ask mode), whether bash is sandboxed, the grants, a prompt that is waiting and for how long; the daemon's build, protocol, pid, node and OS; the toriel settings; the versions of pi and the bundled packages (pinned, installed, shadowed). A `controller` block adds the terminal (TERM, tmux, kitty, ssh) and the toriel and pi versions. A daemon that cannot answer (older, or too slow) leaves a snapshot from the controller's own view of the session, with a note saying so.
- `session.jsonl`: a complete copy of the session file, not redacted.
- `daemon-log.txt`, `permission-decisions.jsonl` (below) and `permission-review.jsonl` (pi-permission-system's own log): the lines in the 30 minutes before the note, from every session on the machine.
- `permission-config.json` (the rules; the project's too when its directory has one), `settings.yaml` and `mcp.yaml` with secrets masked (the value of a key that names a token, secret, password, API key or authorization; every value inside a `headers:` or `env:` block; bearer tokens; `--token x` arguments), `doctor.txt`.
- `manifest.txt`, listing each file with its size, or the reason it is missing: a part that cannot be gathered never loses the others, and a bundle that cannot be written at all still keeps the note.

**Looking after the bundles (ticket 240).** Nothing deletes a bundle by itself (deleting feedback on a timer would be a surprise), and each holds a full session copy, so there are explicit tools, `src/feedback-admin.ts` and `src/feedback-cli.ts`: `toriel feedback list` (newest first, with sizes), `toriel feedback prune [--keep N] [--older-than 30d] [--dry-run]` (whole bundle folders only, by count and/or age; it needs at least one rule, and the notes file `feedback.jsonl` is never touched, so a pruned bundle's note keeps its text) and `toriel feedback export <bundle> [--to DIR]` (the system `tar` into `DIR/feedback-<bundle>.tar.gz`, mode 0600; the output says the session copy is not redacted). `<bundle>` is the folder name or any unique part of it, such as the id `/feedback` printed. `toriel doctor` has a `feedback-size` check that reports the bundle folders once they pass 2 GB (manual fix: prune).

**The permission decision log (ticket 239).** The daemon writes one line per permission prompt to `$XDG_DATA_HOME/toriel/permission-decisions.jsonl` (`TORIEL_DECISIONS` overrides; rotated to `.1` past 8 MB; `src/decision-log.ts`): the time, session and agent, the surfaces, the command or path (shortened), the rule that made pi ask (explicit or the default, with its pattern and origin, as the grants link reported it), whether auto mode was on and the floor reason when it stood aside, **who answered** (`grant`, `auto`, `user`, `deny-after`, or `dropped` when the prompt went away), the answer, how long it waited, whether a controller was attached, and the scope mode. pi's review log records the ask but not who answered it, which is what "auto mode still prompts" needs. Questions that are not permission prompts are not logged.

## Status bar and compaction

The bar under the chat box shows, for the session on screen: name | model
(upstream provider) | state (idle, or what it is doing) | ctx used/max and
percent | thinking level | cost. Gauges (model tier, context fill, effort) run
smoothly from green at 0% to red at 100% in the theme's palette; when the
terminal is narrow the least important segments drop first (thinking level,
model, cost, context), never the name or state. Context and cost come from pi's
own session stats, so they survive a daemon restart; context is unknown (`?`)
right after a compaction until the model's next reply.

Messages sent while a `/compact` is running are held by the daemon (pi itself
refuses prompts then), shown as queued, and delivered in order when it finishes.

Steering into a busy session (a typed prompt or a session-to-session message)
queues in pi and shows on the same strip. Pi's queue updates are the only source
of that state, so whenever the daemon refreshes a child's state it also checks
pi's pending-message count: if pi has nothing queued, it re-announces an empty
queue, so a strip can no longer stick on stale entries after a lost update.

When a session has the session bridge extension (`pi/extensions/toriel-session-bridge.ts`, which adds the command `/toriel-inject`), messages from other sessions skip pi's steering queue entirely: the daemon sends the command over the child's own pipe with an id, and the extension delivers them as `toriel-inject` custom messages - at the next turn boundary mid-run (pi announces these as `entry_appended`), at the settle boundary at the end of a run, or by starting a turn when idle (`message_end`). The daemon confirms each from that announcement, so a lost event cannot strand the message or its strip entry; the strip shows what the bridge still holds. Anything handed to pi that never reached the transcript is put back and sent again; a refused or failed inject falls back to steering; a session that stops with unconfirmed injects says so (`exited` with a reason). Only messages from other sessions take this route, not your own prompts. A session without the bridge (its extension failed to load; see the daemon log) falls back to steering, is marked `sessionBridge: false`, and the switcher notice line counts such sessions. Design notes: docs/design.md, "Session bridge".

A compaction shows as pi's own summary row ("Compacted from N tokens", ctrl-o
expands it). Pi keeps the whole file, so when a session is replayed from its
file the messages the model no longer has (before the first kept entry) are
shown faint above that row. The rewind list marks messages from before a
compaction and warns that rewinding there also undoes the compaction.

## Usage in the status bar

Quota windows (z.ai's 5h / weekly) and LiteLLM budget spend show after the
context figure, e.g. `5h 16% 7d 4%`, colored green to red. They come from a pi
extension, so toriel never handles your API keys: it ships
with toriel and is loaded into every child by flag. It runs
only in children toriel starts, asks pi's own model registry for the key, makes
one request per minute at most, and reports percentages only. To check what
z.ai returns for your key by hand (this sends the key to z.ai's own host):

    curl -s -H "Authorization: Bearer $(jq -r '."zai-coding-cn".key' ~/.pi/agent/auth.json)" \
      https://open.bigmodel.cn/api/monitor/usage/quota/limit | jq .

Providers without an adapter (ollama, plain OpenAI-compatible hosts) show
nothing. See design.md (in this folder) for the adapters, their sources and what is unverified.

## Reconnect, resync and drift

- **Daemon connection lost.** The controller no longer exits. It keeps the screen and the editor text (nothing typed is sent or dropped), shows "daemon connection lost - reconnecting" in the notice line, and retries with backoff (0.5s doubling to 5s, 20 tries; each try starts a daemon if none is running). On reconnect the daemon's initial sync replays every live session's history; each view is then replaced outright, so activity, queue strip, dialogs and unechoed prompts from before the loss are dropped. After the tries run out it exits as before. Requests in flight fail with "daemon connection lost".
- **Drift check.** When a run settles the daemon broadcasts `digest {session, messages, streaming}`, the number of messages a history replay would hold. A controller counts the messages it has seen (the replay's length plus `message_end` / appended custom entries since); if a settled session's counts differ it sends `resync {session}` and the daemon replays that session's history to it alone. A false alarm (a `!command` result, which has no message event) costs one replay.
- **Tools after /reload.** Every child without a profile tool list is started with `--tools +toriel_message,+toriel_schedule_create,+toriel_schedule_list,+toriel_schedule_cancel,+toriel_agent,+toriel_agents,+toriel_usage,+toriel_job` (from `resources.ts`; the two subagent tools only for sessions that may start subagents), so a resume, which restores the tool list recorded in the transcript, still declares the tools of extensions installed since. A profile that lists tools owns its loadout, except that a session the user drives on it also gets `todo_write`, `enter_plan_mode` and `exit_plan_mode` (`SESSION_TOOLS`, appended as bare names: pi refuses to mix them with `+name`), so plan mode can always be left; a subagent (started with `subagent: true`) gets them only when its profile names them (ticket 232).
- **Resources audit.** At daemon start (log) and on the controller's 10-second refresh (notice line) toriel checks that the files listed in `resources.ts` exist in the checkout, and that pi's agent dir holds no old toriel links (left by the removed symlink installer, they would load every extension twice); stale links are named with the `rm` command. It also checks for `pi-permission-system`, which gates the tools your rules mark `ask` but is your own pi package, not shipped by toriel: it warns when the package is not in pi's `packages` (sessions then run without permission prompts) or its `config.json` is missing or invalid (it then asks about everything). Set `warnNoPermissionSystem` to `false` in the toriel settings to silence that check. When the package is set up it also checks the two lines permission grants need (see "Permission grants"): `"toriel-grants"` in its `authorizerChain`, and a `path` rule (`ask` or `deny`; the last matching rule wins, `*` crosses directories, `~` is expanded) covering the grants file; each missing one is named with the line to add. `warnNoPermissionSystem: false` silences these too. All problems found are shown together. The audit never changes anything itself; `toriel doctor --fix` is the one thing that edits, and only when you ask.
- **Prompting a sleeping session (#58).** The first prompt starts the session's child, which takes seconds. The controller allows one such prompt per session file at a time: a repeated enter with the same text is ignored with a notice (its echo is kept), different text typed meanwhile is put back in the editor. The daemon's "changed N seconds ago - may be open in another pi" confirmation is skipped for files toriel itself has run a child on (`handled-files.ts`, persisted in `handled-files.json` under the toriel data dir), so a daemon restart does not ask about toriel's own sessions.
